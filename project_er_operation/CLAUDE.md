# PERO仕様書

ER図作成アプリ「PERO」の仕様書。本書は実装用の指示書として `CLAUDE.md` にも使用する。

## 0. 本書の位置付け

### 0.1 項番IDと報告
1. 項番ID: 「節番号-項目番号」で表す。例: `7-3` は第7節の3番目の項目、`6.2-4` は6.2節の4番目の項目。各節の番号付きリストの1段目を項目とする。
2. 実装後は生成結果レポート(11.1-1)に、項番ごとの実装状況(済/一部/未/仕様差異)を表で記載する。
3. 本書に記載がなく、実装中に決める必要が生じた事項は、最も単純な方法で暫定実装し、「仕様未定義」としてレポートに列挙する。独自の機能追加はしない。
4. 付録Dは、本書で仮定として置いた既定値の一覧。

### 0.2 用語集
| 用語 | 定義 |
|---|---|
| モデル | `.pero` ファイル1つに対応するデータ全体(ルート)。出力ファイル名などのプロパティ(5.1)を持つ |
| エンティティ | テーブルとビューの総称 |
| ERオブジェクト | エンティティとリレーションシップの総称。ID(整数)とロックを持つ |
| 共有リソース | モデルが持つ型(6.3)、メソッド(8.1)、共通列パターン(8.2) |
| ダイアグラム | タブ1枚に対応する表示単位。エンティティの配置(位置・折りたたみ状態)と用紙ページのグリッドを持つ |
| 用紙ページ | ダイアグラム内の印刷単位。行×列のグリッドの1セル |
| キャンバス | ダイアグラムを描画する画面上の領域 |
| 配置 | エンティティをダイアグラムに表示登録すること。位置と折りたたみ状態を持つ。1エンティティは複数のダイアグラムに配置できる |
| 実列 / 共通列 | 実列はテーブルが保存している列。共通列は共通列パターン(8.2)から展開される仮想列 |
| 親 / 子 | リレーションシップの親(参照される側)と子(外部キーを持つ側) |
| 依存関係 | リレーションシップの属性。有効のとき子の外部キー列を子の主キーに含める識別関係(7-6) |
| ポストファイル(post) | SQL生成の変換定義。JavaScriptで記述する(9.6-4) |
| 対象DB | 生成の対象とするデータベースの種類(postgresql / mysql / sqlserver / sqlite) |
| 生成用JSON | ポストファイルへ渡すJSON(付録B)。保存用の `.pero`(付録A)とは別物 |
| エクスポート用 / インポート用ポストファイル | ポストファイルの役割(メタ情報の `role`。9.6-4)。エクスポート用はモデルからSQLを生成する(9.6)。インポート用はSQLを解析してインポート結果(付録E)を返す(9.11)。省略時はエクスポート用 |
| インポート結果 | インポート用ポストファイルが返すJSON(付録E)。アプリがモデルへ変換する |
| 共通ヘルパ | ポストファイルの記述を助けるJavaScriptの部品(`pero.lib.js`。9.12-1) |

### 0.3 v1の対象外
1. ビュー解析(SQL文字列からビュー定義を取り込む機能)
2. データベースへの接続、リバースエンジニアリング
3. (欠番。自己参照のリレーションシップは対応済み。7-1)
4. ビューをソースにしたビュー(ビューのソースはテーブルのみ)
5. 複数モデルの同時編集(複数ウィンドウ、複数ファイルのタブ)
6. 印刷機能(画像/PDF出力のみ)
7. 多言語表示(UIは日本語のみ)、Windows以外のOS
8. 同梱(`postgresql.post`、`mysql.post`、`sqlserver.post`)以外のDB別ポストファイル(sqlite用など)

## 1. 概要
1. ER図を作成、編集できるWindows 10/11向けデスクトップアプリケーション(Flutter製)。
2. 作成したデータ、設定はJSONで保存、復元できる。
   3. データファイルの拡張子は `pero`。ユーザーがアクセスできる範囲で選択して自由な場所に保存できる。
   4. 設定ファイルは実行ファイル直下に保存する(10.1)。
5. SQLを生成できる。
   6. 生成にポストファイル(コード変換定義ファイル。拡張子は `post`)を使用する。
   7. ポストファイルはJavaScriptで定義する(9.6-4)。
8. GUI
   9. タブ(ダイアグラム)による機能別ページ管理。ユーザーが自由に追加削除でき、エンティティを表示するダイアグラムを選択できる。タブをまたぐリレーションシップは、相手エンティティ名を線の先端に表示する(5.2-8)。
   10. サイドメニューからエンティティを選択し、ドラッグ&ドロップで配置する。
   11. ドラッグ&ドロップでオブジェクトを移動する。
   12. 複数パターンの共通列を、テーブル物理名の正規表現で自動付与する(8.2)。
   13. 右クリックのコンテキストメニュー(4.4)。
   14. ビュー生成: エンティティを組み合わせるダイアログから、または関数の結果から、ビューを生成する。列に別名を与えられる(6.6)。
15. SQLインポート: SQL(DDL)を、データベースの種類に応じたインポート用ポストファイルで解析し、モデルとして開く、または現在のモデルへ追加する。解析できないものはログに残し、別ファイルへ保存できる(9.11)。

## 2. 技術要件
1. 対象OSはWindows 10/11 64bit。Flutterのデスクトップ(Windows)アプリとする。
2. Flutterはstableの特定バージョンに固定し(pubspec.yaml、またはFVMの設定)、Dartは3系とする。依存パッケージのバージョンは `pubspec.lock` をコミットして固定する。
3. 次のパッケージを候補とする。採用時に最新版とWindows対応を確認し、使えない場合は代替を選んで理由をレポートに記載する。
   4. 状態管理: Riverpod(riverpod_generator)
   5. 不変モデルとJSON: freezed、json_serializable
   6. JavaScript実行: flutter_js
   7. ファイル選択: file_selector
   8. ウィンドウ制御: window_manager
   9. パス取得: path_provider
   10. PDF出力: pdf
11. 描画: キャンバスは `CustomPainter` で描く。ヒットテストはモデル座標系で自前実装する。画像/PDF出力は同じPainterを倍率指定で描画して共用する。画面表示では、エンティティ1つ分の描画結果(Picture)と寸法・列行をバッファリング(キャッシュ)し、モデル・表示設定・テーマが変わるまで再利用する(ドラッグ中は同じ描画結果を位置だけ変えて描く)。倍率が40%未満のときは、列行を省略して見出しだけを描く。ズーム・スクロールは、画面全体を再構築せずキャンバスとズーム表示だけを更新する。
12. レイヤ: model(純Dart) / command(純Dart) / persistence(純Dart) / generation(純Dart) / UI。UIからmodel側への依存のみとし、逆方向の依存を作らない。純Dart層はFlutterをimportしない。
13. JavaScript実行は `PostRunner` インターフェースの背後に隔離する。実行は別Isolateで行い、UIをブロックしない。
14. 単一インスタンスで動作する(2つ目の起動は既存ウィンドウへファイルパスを渡して終了する)。`.pero` の関連付け、およびコマンドライン引数でのファイル指定に対応する。
15. 性能目標: テーブル200、列の合計3000、リレーションシップ300のモデルで、パン・ズーム・ドラッグが体感できる遅延なく動作する(目安30fps以上)。
16. 文字コードはUTF-8(BOMなし)。UI文言は1か所(`lib/common` 配下)に集約し、将来の多言語化に備える。
17. ログ、キャッシュ、バックアップの既定の保存先は `%LOCALAPPDATA%\PERO\` 配下とする。

## 3. 画面構成

### 3.1 メイン画面
1. 構成(上から): タイトルバー、トップバー(検索。3.9)、本体、ステータスバー。本体は左から、サイドメニュー(機能別のタブ。3.3)、キャンバス(上部にタブバー)、右ペイン(上=プロパティ、下=テーブルリスト)。
2. 右ペインの幅は既定でウィンドウ幅の25%。プロパティとテーブルリストの高さは既定で各50%。スプリッタのドラッグで変更でき、割合として設定に保存して次回起動時に使用する。最小は、右ペイン幅240px、各ペイン高さ120px。
3. サイドメニューの幅は200px固定。メニュー項目は折り返さず、1行で表示する(収まらないときは文字を縮小する)。
4. ウィンドウの最小サイズは1024×700、初期サイズは1280×800(画面中央)。位置、サイズ、最大化状態を設定に保存して次回起動時に使用する。
5. 設定画面は、ファイルメニューから開くモーダルダイアログ(3.8)。
6. ダイアグラムの表示領域を広げるため、サイドメニューと右ペインは、タブバーの左端・右端のボタンで、折りたたみ/スライドインできる。開閉の状態は設定に保存して次回起動時に使用する(既定は両方とも開く)。ペインを閉じている間は、そのペインへの操作(キー入力、クリック)は受け付けない。

### 3.2 タブバー
1. キャンバスの上部に置く。1タブ=1ダイアグラム。
2. 「+」ボタンで追加、「×」で閉じる(削除)、ダブルクリックで名前変更、ドラッグで並べ替え。ダイアグラムは最低1つ必要で、最後の1つは削除できない。
3. 新規ダイアグラムの名前は「ダイアグラムN」(Nは未使用の最小の正の整数)。名前はモデル内で重複できない。
4. 削除時は確認ダイアログを表示する。削除されるのは配置だけで、エンティティはモデルに残る。
5. タブが画面の幅に収まらないとき、タブの並びの両端に「◀」「▶」ボタンを表示し、押すと表示範囲を左右へ移動する(1回に240px)。端に達した側のボタンは無効にする。収まるときは表示しない。表示するダイアグラムが切り替わったとき(ショートカット、検索による移動、列ドラッグ中のタブ切替を含む)は、そのタブが見える位置までスクロールする。

### 3.3 サイドメニュー
1. キャンバスの左に置く。サイドメニューは機能別のタブに分ける。タブは「追加」(項目は「テーブル」「結合ビュー」「関数ビュー」「SQLビュー」)、「ファイル」(4.1のメニュー)、「操作」(4.2のメニュー)、「RUN」(4.3のメニュー)。メニュー項目には、ショートカットのキーを小さく併記し、有効でない項目は無効表示にする。ショートカットのキー操作は従来どおり(4.5)。項目の文字は折り返さず、1行で表示する(3.1-3)。
2. 項目をキャンバスへドラッグ&ドロップすると、ドロップ位置を左上として追加する。クリックのみの場合は操作メニューと同じ動作(4.2-2、4.2-3)。
3. ビューはドロップ後に定義ダイアログ(6.6)を開く。キャンセルすると追加を中止する。

### 3.4 キャンバス操作
1. 移動: エンティティのヘッダをドラッグして移動する(本体の列行のドラッグでは移動しない。3.4-9)。移動は10pxのグリッドにスナップする(Alt押下中は解除。設定でスナップ幅を変更でき、0で無効)。ドラッグ中は、ドラッグしているエンティティを半透明にしてポインタに追従させ、ドラッグ元の位置には何も表示しない(元の位置は、ドロップするまで空く)。
2. 選択: クリックで単独選択。Shift/Ctrlを押しながらクリックでトグル追加。空白のドラッグで矩形選択(矩形に一部でも含まれていれば選択する)。Ctrl+Aで現在のダイアグラムの全選択。空白クリックまたはEscで選択解除。
3. 複数選択中のドラッグは、選択中のすべてを同時に移動する(ロック中は動かない。5.3-2)。
4. パン: 中ボタンのドラッグ、またはSpaceを押しながらドラッグ。ホイールで縦スクロール、Shift+ホイールで横スクロール。
5. ズーム: Ctrl+ホイール(カーソル位置が中心)。範囲は25〜400%。Ctrl+0で100%。
6. 折りたたみ: テーブル/ビューのヘッダの折りたたみボタン(▼/▶)で切り替える(Undo対象)。
7. テーブルまたはビューのダブルクリックで、プロパティペインの論理名入力にフォーカスを移す。
8. オブジェクトの移動中は、ページ境界を超えた場合の用紙ページの追加・削除(5.2-4)を、ドロップ時に評価する。
9. リレーションシップの構築: テーブルの列行をドラッグして、別のテーブル(エンティティ、または、その列行)へドロップするとリレーションシップを追加する。ドラッグした列が親側(主キーまたはユニーク制約の列に限る)、ドロップ先が子側。ドロップ先が列行のときは、その列を対応する外部キー列にする(7-5)。ドラッグ中は、ドラッグ元の列行の強調、元からポインタまでの線、ポインタ位置の列の画像、ドロップ先の強調を表示する。空白、ビューへのドロップは何もしない。同じテーブルへのドロップは、別の列行へドロップしたときだけ、自己参照のリレーションシップを追加する(7-1)。 ドラッグ中に、別のダイアグラムのタブの上へポインタを約0.6秒置くと、そのタブを強調し、そのダイアグラムへ切り替える。ドラッグは続き、切り替えたダイアグラムのテーブル(元のテーブルが配置されていなくてもよい)へドロップできる。

### 3.5 テーブルリスト
1. 右ペイン下。ヘッダは「テーブルリスト（N）」(Nはビューを含むエンティティの総数)。
2. 1行ずつ表示する: 「論理名（物理名）」と列数(共通列を含む)。ビューには先頭に「VIEW」の表示を付ける。テーブルがトリガーを持つときは、列数の前に「トリガーN」(Nはトリガーの数)を表示する。並びはID昇順。
3. 現在のダイアグラムに配置されていないエンティティは灰色で表示する。
4. クリックでキャンバスの選択と同期する(配置済みならその位置へスクロール)。ダブルクリックで、未配置なら現在のダイアグラムに配置する。
5. ヘッダ下に検索ボックスを置く(論理名・物理名の部分一致、大文字小文字を区別しない)。

### 3.6 プロパティペイン
1. 右ペイン上。何も選択していないときは、モデルのプロパティ(5.1)と、現在のダイアグラムのプロパティ(名前、用紙サイズ、向き、ページ行数・列数の表示)を表示する。
2. 1つ選択しているときは、そのオブジェクトの編集できる項目を表示する(テーブル=6.1-9、ビュー=6.6、リレーションシップ=7-4)。
3. 複数選択しているときは「N個選択」と、共通項目(ロックの一括切替)だけを表示する。
4. ロック中のオブジェクトは、ロック以外の項目を無効表示にする(5.3-2)。
5. 値の確定はEnterまたはフォーカス喪失で行い、1回の確定を1コマンドとする(9.1-3)。入力エラーは赤枠とメッセージで示し、確定せず元の値に戻す。
6. 共通列(仮想列)の項目は読み取り専用で表示し、所属するパターン名を示す。
7. 表示の構成: 項目は機能別のタブに分けて表示する(スクロール量を減らし、項目の境目を明確にするため)。選択していないとき=「モデル」「ダイアグラム」。テーブル=「基本」(論理名、物理名、コメント、ロック)、「列」、「制約」(インデックス、ユニーク)、「トリガー」、「クエリ」(生成前・生成後)。ビュー=「基本」(論理名、物理名、コメント、ロック)、「定義」、「クエリ」。リレーションシップ=「基本」(方向、依存関係、多重度、ロック)、「列対応」、「参照規則」(外部キー制約名、ON DELETE、ON UPDATE)。選択するオブジェクトの種類が同じ間は、選択中のタブを保持する。
8. 入力欄は1項目1行で縦に並べる(列の項目も、1列につき項目ごとに1行)。ラベルは入力欄の上に置き、入力欄同士の間隔(行間)を十分にとって、境界が狭くならないようにする。

### 3.7 タイトルバー・ステータスバー
1. タイトルバー: `ファイル名[*] - PERO`。未保存の新規は「無題」。`*` は未保存の変更があることを示す(4.1-8)。
2. ステータスバー: 左に通知メッセージ(設定ファイルのフォールバック、バックアップ失敗など)、右に選択数とズーム率。ズーム率のクリックで100%に戻す。

### 3.8 設定画面
1. ファイルメニューの「設定」で開くモーダルダイアログ。左にカテゴリ一覧、右に項目を表示する。
2. ボタン: OK(検証・反映・保存して閉じる)、キャンセル、適用、「このカテゴリを既定に戻す」、「すべて既定に戻す」。
3. 項目は10.2。

### 3.9 検索
1. トップバー(画面上部)の中央に検索ボックスを置く。幅は20文字程度。右側に「正規表現を使う」のトグルと、範囲のプルダウンを置く。3つの部品の高さ(32px)と枠線の色をそろえる。条件を入力すると、入力のたびに検索する(Undoの対象外)。
2. 範囲: 全て / テーブル / ビュー / 列 / 関数 / トリガー / コメント。既定は「全て」(すべての範囲の和)。
3. 大文字小文字は区別しない。正規表現が不正なときは、ヒットなしとし、「正規表現が不正です」と表示する。検索ボックスの右に、ヒット件数を表示する。
4. 検索の対象
   5. テーブル、ビュー: 論理名、物理名。
   6. 列: 論理名、物理名(テーブルの実列と共通列、ビューの出力列・戻り列)。
   7. 関数: 種別がファンクションのメソッドの名前、定義(本体、呼出し式)。
   8. トリガー: トリガーの名前、条件、引数、入力の本体、パブリックのトリガーが使うメソッドの名前と本体。
   9. コメント: テーブル、ビュー、列のコメント。
10. ヒットしたオブジェクトは、キャンバス上でハイライト表示する。画像出力(9.8)には含めない。
   11. 入れ子の外側(親。テーブル、ビュー、関数、トリガーなど)は薄く、内側(子。列、関数の定義、トリガーの中のメソッドなど)は濃く表示する。
   12. テーブル、ビュー自身がヒットしたときは、ヘッダを濃く、本体を薄く表示する。列がヒットしたときは、その列行を濃く、テーブルを薄く表示する。
   13. 関数は、使っている側(列のデフォルトのメソッド、関数ビュー)を表示先とする。名前のヒットは使っている側を薄く、定義のヒットは使っている列行と関数ビューのヘッダを濃く表示する。
   14. トリガーは、トリガーを持つテーブルを表示先とする。トリガー自身のヒットはテーブルを薄く、トリガーの中のメソッド(パブリック)または入力の本体のヒットはテーブルのヘッダを濃く表示する。
15. 現在のダイアグラムに配置されていないエンティティは、ハイライトの対象にならない(テーブルリストの検索ボックス。3.5-5は別の機能)。
16. ヒットへの移動: 検索ボックスの右に、前(↑)と次(↓)のアイコンボタンを置く。押すたびに、ヒットしたエンティティ(ID昇順)へ順に移動し、最後の次は先頭、先頭の前は最後へ循環する。検索ボックスで Enter は次、Shift+Enter は前。移動先が現在のダイアグラムに配置されていないときは、配置している最初のダイアグラム(タブ順)へ切り替える。どのダイアグラムにも配置されていないエンティティは飛ばす。移動先は、画面の中央へスクロールする(選択は変えない)。ヒットがないときは、ボタンを無効にする。検索条件を変えると、移動の位置は先頭に戻る。

## 4. メニュー
メニューは、サイドメニューのタブ(3.3)に表示する。上部のメニューバーは持たない。

### 4.1 "ファイル"メニュー
1. 新規作成(Ctrl+N)
   2. 未保存の変更があれば未保存確認(4.1-8)を行う。
   3. 空のモデルを作る: ダイアグラム1つ(「ダイアグラム1」、1×1の用紙ページ、設定の既定サイズと向き)、型は設定の型テーブルの複製、メソッドは標準メソッド「空文字」(8.1-15)のみ、共通列パターンは空、対象DBはpostgresql、ポストファイルのパスは設定の既定。
4. ファイルを開く(Ctrl+O)
   5. 未保存確認(4.1-8)の後、ファイルを開くダイアログ(フィルタ `*.pero`)を表示する。
   6. 既定のフォルダは、前回開いた/保存したフォルダ。無ければマイドキュメント。
   7. 読込後にデータ整合性確認(9.4)を行う。失敗した場合はエラーを表示し、現在のモデルを維持する。読込(読み込みと復元)は別Isolateで行い、読込中は、画面全体を覆うオーバーレイと、ローディング(くるくる)とメッセージ「{ファイル名} を読み込み中…」を表示する。読み込んだ後の最初の画面の描画が終わるまで表示し、失敗したときも必ず消す。表示中は、画面の操作(クリック)を受け付けず、もう一度開く操作も受け付けない。
   8. 成功したら最近使ったファイルとして記録する。
9. ファイルに保存(Ctrl+Shift+S)
   10. 保存ダイアログの既定のフォルダは、既存ファイルを開いているときはそのフォルダ、無ければ前回保存したフォルダ、無ければマイドキュメント。既定のファイル名は現在のファイル名、無ければ「無題.pero」。拡張子 `.pero` を付与する。
   11. データ整合性確認(9.4)を行い、一時ファイルに書いてからリネームして保存する(途中で失敗しても元のファイルを壊さない)。
   12. 成功したら、現在のファイルパスを更新し、未保存状態を解除し、最近使ったファイルとして記録し、キャッシュの基点を更新する(9.2-2)。
   13. 書込みに失敗した場合はエラーを表示し、未保存状態を維持する。
14. 上書き保存(Ctrl+S)
   15. 新規作成でまだ保存していない場合はメニュー項目を無効にする。このとき Ctrl+S は「ファイルに保存」を起動する。
   16. 同じパスにデータを保存する。保存手順は4.1-3の2〜4と同じ。
17. 最近使ったファイル
   18. 設定(10.2)の数だけ、新しい順に表示する。
   19. 選択したときに、未保存確認(4.1-8)の後でそのファイルを開く。存在しない場合はエラーを表示して一覧から削除する。
   20. 設定の数が0のとき、この項目は表示しない。
21. 設定(Ctrl+,): 設定画面(3.8)を開く。
22. 終了(Alt+F4): 未保存確認(4.1-8)の後、正常終了処理(設定の保存、キャッシュとセッションロックの削除。9.2-4)を行う。
23. 未保存確認: 未保存の変更(最後に保存または読み込んだ時点のUndo履歴の位置と、現在の位置が異なる状態)があるとき、新規作成、ファイルを開く、最近使ったファイル、終了、ウィンドウを閉じる操作の前に「保存 / 保存しない / キャンセル」のダイアログを表示する。
   24. 保存: 上書き保存(未保存の新規は「ファイルに保存」)。保存ダイアログをキャンセルした場合は操作全体をキャンセルする。
   25. 保存しない: 変更を破棄して操作を続行する。
   26. キャンセル: 操作を中止する。
27. SQLインポート: SQLインポートのダイアログ(9.11-2)を開く。メニューでは「最近使ったファイル」の下に表示する。

### 4.2 "操作"メニュー
1. 元に戻す(Ctrl+Z) / やり直し(Ctrl+Y、Ctrl+Shift+Z)。履歴がないとき無効(9.1)。
2. テーブルの追加: 常に有効。追加位置は、メニューからは表示領域の中央、右クリックメニューからは右クリックした位置、サイドメニューからはドロップ位置。追加するテーブルは、論理名「テーブルN」、物理名「table_N」(Nは未使用の最小の正の整数)、列は1つ(論理名「ID」、物理名「id」、型auto、PK)。現在のダイアグラムに配置する。
3. ビューの追加(結合ビュー / 関数ビュー / SQLビュー): 常に有効。定義ダイアログ(6.6)を開き、OKで追加して現在のダイアグラムに配置する。
4. 削除
   5. このダイアグラムから外す(Delete): エンティティが選択されていて、すべてロックされていないとき有効。配置だけを削除し、エンティティはモデルに残る。
   6. モデルから削除(Ctrl+Delete): エンティティが選択されていて、すべてロックされていないとき有効。確認ダイアログに削除対象と、巻き込まれるリレーションシップの一覧を表示する。削除の取り扱いは6.1-12。
   7. リレーションシップが選択されているときの Delete は、4.2-6と同じ。
8. リレーションシップの追加: テーブルがちょうど1つ(自己参照。7-1)または2つ選択されていて、次をすべて満たすとき有効。
   9. 選択したテーブルがどれもロックされていない(5.3-2)。
   10. (欠番。自己参照を許可する。7-1)
   11. 親になるテーブルが主キー(またはユニーク制約)を持つ。
12. リレーションシップの削除: リレーションシップが選択されていて、端点のテーブルがどちらもロックされておらず、リレーションシップ自身もロックされていないとき有効。
13. コピー(Ctrl+C) / 貼り付け(Ctrl+V) / 複製(Ctrl+D)
   14. コピー対象は、選択したエンティティと、その選択エンティティ同士を結ぶリレーションシップ。クリップボードはアプリ内のメモリに保持し、モデルを切り替える(新規作成、ファイルを開く)とクリアする。
   15. 貼り付けは、新しいIDを採番し、位置を元から(20,20)ずらして現在のダイアグラムに配置する。論理名は「{元}のコピー」、物理名は「{元}_copy」(重複時は `_copy2`、`_copy3` ...)。制約名、トリガー名の手動入力値にも `_copy` を付けて重複を避ける。ロックは解除した状態にする。
   16. 複製はコピーと貼り付けを続けて行う。
17. 全選択(Ctrl+A): 現在のダイアグラムに配置されたオブジェクトをすべて選択する。
18. 自動配置: 9.9。
19. 管理ダイアログ: メソッド管理(8.1)、共通列パターン管理(8.2)、型管理(6.3-4)。
20. ダイアグラム: 追加、名前変更、削除(3.2と同じ動作)。

### 4.3 "RUN"メニュー
1. 生成実行(F5): 9.6。
2. JSON出力: 9.7。
3. 画像出力: 9.8。

### 4.4 コンテキストメニュー
1. キャンバスまたは用紙ページの空白: テーブルの追加、ビューの追加(結合 / 関数 / SQL)、貼り付け(コピー済みのとき)、全選択、自動配置。
2. テーブルまたはビュー上
   3. プロパティ編集(プロパティペインにフォーカスを移す)
   4. このダイアグラムから外す
   5. モデルから削除
   6. 表示するダイアグラム(サブメニュー。ダイアグラムごとのチェックで配置と取り外しを切り替える)
   7. リレーションシップの追加(テーブルが2つ選択されているときのみ)
   8. コピー / 複製
   9. ロック / ロック解除
10. リレーションシップ上: 削除、ロック / ロック解除。
11. 複数選択上: 上記のうち該当する項目(削除、ロックの一括切替)。
12. 未選択のオブジェクト上で右クリックしたときは、そのオブジェクトを単独で選択してからメニューを表示する。選択中のオブジェクト上で右クリックしたときは、選択を維持する。
13. 各項目の有効条件は4.2と同じ。

## 5. モデルとダイアグラム

### 5.1 モデル
1. モデルはシステムが決定したIDを持つ。
2. モデルのプロパティ(何も選択していないときにプロパティペインへ表示する)
   3. 出力ファイル名(拡張子なし。生成ファイルの名前に使う。9.6-1)
   4. 出力フォルダ(生成ファイルの保存先。9.6-1)
   5. 対象のデータベース(postgresql / mysql / sqlserver / sqlite。既定はpostgresql)。候補は、ポストファイルがある種類だけ(9.10-3)。ポストファイルを選ぶと、そのメタ情報の種類に決まる(9.10-2)。
   6. ポストファイルのパス(既定は設定による。9.6-1)。ポストフォルダにあるポストファイルから選べる(9.10-1)。
   7. 開始クエリ(生成ファイルの先頭に出力する複数行テキスト)
   8. 終了クエリ(生成ファイルの末尾に出力する複数行テキスト) 出力設定として、スキーマ(出力に使うスキーマ名。ダイアグラムのスキーマが空のときに使う)と、「出力にスキーマを含める」(既定は無効)を持つ(5.2-1、9.6-25)。
9. 共有リソース(型、メソッド、共通列パターン)、エンティティ、リレーションシップ、ダイアグラムをモデルが持つ。保存形式は付録A。

### 5.2 ダイアグラムと用紙ページ
1. ダイアグラムは、ID、名前、用紙サイズ(A0〜A4)、向き(横/縦)、用紙ページのグリッド(行数×列数)、配置のリスト、表示状態(ズーム、スクロール位置)を持つ。モデルは最低1つのダイアグラムを持つ。 ダイアグラムはスキーマ(文字列。空のときはモデルのスキーマを使う)も持つ。エンティティのスキーマは、そのエンティティを配置している最初のダイアグラム(タブ順)のスキーマ(空ならモデルのスキーマ)で決める。どのダイアグラムにも配置されていないときは、モデルのスキーマとする。
2. 座標系は論理px(96dpi基準)。原点はグリッドの左上。用紙サイズ(mmからの換算、四捨五入)は次のとおり。解像度設定(10.2)は画像出力の倍率(dpi÷96)として使う。

   | 用紙 | 縦(幅×高さ) | 横(幅×高さ) |
   |---|---|---|
   | A0 | 3179×4494 | 4494×3179 |
   | A1 | 2245×3179 | 3179×2245 |
   | A2 | 1587×2245 | 2245×1587 |
   | A3 | 1123×1587 | 1587×1123 |
   | A4 | 794×1123 | 1123×794 |
3. 用紙ページは、ダイアグラムのグリッドの1セルで、(行, 列)で識別する(IDは持たない)。ページ境界は破線で描く。新規ダイアグラムは1×1。
4. 用紙ページの増減: ドロップ時に評価する。
   5. エンティティの矩形(位置と6.1-7の寸法)がグリッドの外へはみ出す場合、はみ出した方向(上下左右)に、矩形が収まるまで行または列を追加する。
   6. 端の行(列)にあるすべての用紙ページに、エンティティの矩形が1つも重ならない場合、その行(列)を削除する(中抜けは作らない。最低1×1)。
   7. 左または上に追加/削除した場合は、すべての配置の座標を、追加/削除したページの幅(高さ)だけ平行移動して原点を維持する(画面上の見た目とスクロール位置は変えない)。
   8. エンティティの矩形が複数のページにまたがることを許す。
9. 用紙サイズ・向きの変更はプロパティで行う。既存の配置座標は変更せず、グリッドを4の規則で再計算する。用紙サイズ・向きはダイアグラムごとに独立している。
10. 新規ダイアグラムの用紙サイズ・向きの既定は、設定(10.2)による。
11. エンティティは複数のダイアグラムに配置できる。位置と折りたたみ状態は配置ごとに持つ。どのダイアグラムにも配置されていないエンティティも、モデルには存在する(テーブルリストに灰色で表示される)。
12. リレーションシップは、端点のエンティティの少なくとも片方が配置されているダイアグラムに表示する。
   13. 両端が配置されている: 直線で結ぶ(7-2)。
   14. 片端のみ配置されている: 配置されている側のエンティティの矩形の右辺から右へ40pxの短い線を引き、先端に相手エンティティの「論理名（物理名）」を表示する。同じ側に複数ある場合は縦に16pxずつずらす。
   15. 両端とも配置されていない: 表示しない。

### 5.3 ERオブジェクト共通
1. すべてのERオブジェクトは、システムが決定したID(整数。付録A)と、ロックのパラメータ(既定は無効)を持つ。
2. ロックが有効のときの動作
   3. エンティティ: 移動、プロパティの編集、削除(「外す」と「モデルから削除」)、自動配置による移動を禁止する。折りたたみの切替と、他のダイアグラムへの配置の追加は許す。
   4. ロック中のテーブルを端点とするリレーションシップの追加と削除、およびそのテーブルへの外部キー列の自動作成を禁止する。
   5. リレーションシップ: 削除とプロパティの編集を禁止する。
   6. 間接的な影響(相手端のテーブルの削除、メソッドや型の削除による参照解除、列の削除による参照解除など)がロック中のオブジェクトに及ぶ操作は実行せず、ロックを解除するよう促すメッセージを表示する。
   7. プロパティペインでは、ロック以外の項目を無効表示にする。ロックの切替だけは常に可能。
   8. 共通列パターン(8.2)の変更は、仮想列を変えるだけなのでロックの影響を受けない。
9. 複数選択して移動するとき、ロック中のオブジェクトは動かず、ほかは移動する。
10. 選択の操作は3.4-2。

## 6. エンティティ

### 6.1 テーブル
1. テーブルはモデルに属し、複数のダイアグラムに配置できる(5.2-7)。
2. 追加方法は、サイドメニューからのドラッグ&ドロップ、操作メニュー、キャンバス・用紙ページの空白の右クリックメニュー(4.2-2)。
3. 表示(ヘッダ): タイトルは設定(10.2)の「ヘッダ表示」に従い、「論理名（物理名）」(両方ON)、論理名のみ、物理名のみのいずれか。折りたたみボタン(▼/▶)を持ち、ロック中はロックアイコンを表示する。
4. 表示(列行): 1列=1行。左から順に次の項目を表示し、各項目の幅はテーブル内で全行そろえる(項目ごとの最大幅)。
   5. PKアイコン(PKの列のみ。キーアイコン)
   6. NotNullマーク(NotNullの列。常に表示)
   7. 論理名(設定による)
   8. 物理名(設定による)
   9. 型名(設定による。パラメータを含む。例: `varchar(255)`)
   10. デフォルト値(設定による。値の種別はその値、メソッドの種別はメソッド名)
   11. コメント(設定による)
   12. デフォルトありアイコン(常に表示)
13. 共通列(8.2)は、パターンの位置が「先頭」なら実列の前、「末尾」なら実列の後に、パターンの並び順で、薄色・斜体の読み取り専用行として表示する。
14. 外部キー列(リレーションシップの子側の列として割り当てられている列。7-4)は、背景色(設定の「外部キー列の背景色」)を変える。
15. 寸法: 幅は列行の最大幅に左右余白(各8px)を加えた値(最小160px、最大480px。超過分は末尾を「…」で省略)。高さはヘッダ + 行数 × 行高(標準文字の高さ + 上下余白各4px)。ユーザーによるサイズ変更はできない。
16. 折りたたみ: ヘッダのみを表示する。状態は配置ごとに保存する(5.2-7)。
17. プロパティ(プロパティペイン)
   18. 論理名
   19. 物理名
   20. コメント
   21. 列: 一覧(行表示)。追加ボタン、選択行の削除ボタン、ドラッグ&ドロップによる順の変更。各列の項目は6.2。共通列は一覧の末尾に読み取り専用で表示する。
   22. 制約: インデックス、ユニーク、CHECK制約(6.4)
   23. テーブル生成前実行クエリ(複数行テキスト)
   24. テーブル生成後実行クエリ(複数行テキスト)
   25. トリガー(6.5)
   26. ロック(5.3)
27. 名称の入力規則は6.7。
28. 追加時の既定値は4.2-2。
29. 削除
    1. 「このダイアグラムから外す」は、そのダイアグラムの配置を削除する。
    2. 「モデルから削除」は、テーブルと、すべての配置と、そのテーブルを端点とするすべてのリレーションシップを削除する。確認ダイアログに削除対象と巻き込まれるリレーションシップの一覧を表示する。
    3. そのテーブルをソースにしているビュー(6.6)がある場合は、削除できない。ビューの一覧を表示し、先にビューの修正または削除を促す。
    4. ロック中のテーブルは削除できない(5.3-2)。巻き込まれるリレーションシップの端点にロック中のテーブルがある場合も、削除できない。

### 6.2 列
1. 列はテーブルに属し、テーブル間を移動できない。順はプロパティの一覧でドラッグ&ドロップして変更する。
2. 列のプロパティ
   3. 論理名
   4. 物理名
   5. 型(6.3)と、型が必要とするパラメータ(長さ、または精度とスケール。必要なものだけを表示する)
   6. PK
   7. Null許可(NotNullの逆)
   8. デフォルト(6.2-4)
   9. コメント
10. PK: 列のチェックで指定する。複数列で複合主キーになり、キーの順は列の並び順で決まる。PKの列はNotNull固定とし、Null許可を変更できない。
11. デフォルト: 種別を「なし / 値 / メソッド / 式」のラジオで選ぶ。
   12. 値: 型に合わせた文字列。空にはできない。引用符の要否は、生成用JSONの `typeCategory`(付録B)を使ってポストファイル側で判断する。
   13. メソッド: 種別がファンクションの登録メソッド(8.1)から選ぶ。出力は、対象DBの呼出し式(8.1-3)。 値は空にできないため、空文字のデフォルトは、標準メソッド「空文字」(8.1-15。外部定義、呼出し式 `''`)で表す。
   14. 種別を切り替えても他方の入力値は保持するが、出力には現在の種別のものだけを使う。 式: 文字列(例 `CURRENT_DATE + 30`)。空にはできない。引用符などを含めて、そのまま出力する(生成用JSONの `default.expression`)。
   15. 型が `auto`(自動採番)の列は、種別を「なし」に固定し、変更できない。
16. 自動採番: 型が `auto` の列は、1テーブルに1つまで(9.5)。
17. 追加時の既定値: 論理名「列N」、物理名「column_N」(Nは未使用の最小の正の整数)、型は `varchar`(長さ255)、Null許可、デフォルトなし。
18. 削除したときの影響: 確認ダイアログに影響の一覧を表示し、確認後に次を1コマンドで行う(ロック中のエンティティに及ぶ場合は5.3-2-4)。
   19. その列を含むインデックス/ユニーク(6.4): 列を除外する。列が0になる制約は削除する。
   20. その列を列対応に含むリレーションシップ(7-4): リレーションシップを削除する。
   21. その列をビュー(6.6)が出力列または結合条件に使っている場合は、削除できない。ビューの一覧を表示し、先にビューの修正を促す。
22. 共通列の削除影響(パターンの列の削除、または展開の変更)は8.2-5。

### 6.3 型
1. 型の定義(モデルに保存する)
   2. ID(標準型は固定のキー、カスタム型は `custom_` + 連番)
   3. 表示名(アプリ上の表示に使う)
   4. パラメータ種別(なし / 長さ / 精度とスケール)と、その既定値
   5. カテゴリ(number / string / boolean / datetime / binary / json / auto)
   6. 対象DBごとの物理名テンプレート(クエリ出力時に使う)。テンプレートの中の `{length}`、`{precision}`、`{scale}` を、列のパラメータで置換する。
7. 標準型は付録C。標準型は削除できない。物理名テンプレートは編集でき、「初期値に戻す」で付録Cの値に戻せる。
8. カスタム型は追加、変更、削除ができる。 ユーザー定義型(複合型、列挙型)もカスタム型の一種で、型管理で追加できる。複合型は項目(名前と型)の一覧、列挙型は値の一覧を持ち、型の名前を PostgreSQL の物理名テンプレートとする(他のDBは空)。生成では、テーブルより前に `CREATE TYPE` を出力する(9.6-7)。使用中の型の削除(6.3-9)では、複合型の項目も付け替える。 ユーザー定義型は、コメント(`COMMENT ON TYPE` で出力する)とスキーマ(空のときはモデルのスキーマ)も持つ。生成では、型の名前、`COMMENT ON TYPE`、その型を使う列・ビューの戻り列の型に、スキーマを付ける(出力にスキーマを含めるとき。9.6-25)。長さを指定しない `varchar` は、標準型「varchar(長さなし)」(付録C)を使う。
9. 型の編集画面は、操作メニューの「型管理」(モデルの型)と、設定画面の型テーブル(新規モデルの雛形)で、同じ部品を共用する。
10. 設定の型テーブルは、新規作成時にモデルへ複製される雛形。モデルの型はモデル内に保存し、設定の変更は既存のモデルに影響しない(別のPCで開いても型が失われない)。
11. 使用中の型の削除: 使用している列とビューの件数を警告し、置換先の型を必ず選ばせる。確認後に、すべての参照を置換先へ付け替えて1コマンドで削除する。使用中の型は、パラメータ種別を変更できない。ロック中のエンティティが使用している場合は実行できない(5.3-2-4)。
12. 生成用JSONには、対象DBのテンプレートをパラメータ展開した文字列を `type` として渡す(付録B)。対象DBのテンプレートが未定義の型を使っている場合は、生成前検証のエラー(9.5)。
13. リレーションシップで自動作成する外部キー列の型は、親列と同一の型(`auto` は `integer` に置き換える。7-5)。

### 6.4 制約
1. 主キー: 列のPK指定(6.2-3)から導出する。制約名は「プリフィクス + テーブル物理名 + サフィックス」で、プリフィクスとサフィックスは設定(10.2)による(既定は空と `_pk`)。
2. インデックスとユニーク: テーブルがそれぞれ複数を持てる。各制約は次を持つ。
   3. 制約名: 名前の決め方(自動 / 手動)を選ぶ。自動の名前は、インデックスは `{テーブル物理名}_idx{n}`、ユニークは `{テーブル物理名}_unq{n}`(nはその種類のリスト内の位置。1始まり)。自動の名前はテーブル名の変更と並べ替えに追従して動的に決まる。手動の名前は入力必須で、モデル内で重複できない(6.7)。
   4. 列: 実列と共通列(8.2)から1列以上を選び、順を指定する(ドラッグ&ドロップで変更)。 ユニークは「NULLを同値として扱う」(NULLS NOT DISTINCT。既定は無効)も持つ。
5. 外部キー制約は7で定義する。
6. CHECK制約: テーブルは複数のCHECK制約を持てる。名前の決め方(自動 / 手動)と検査式(括弧の内側の文字列。そのまま出力する)を持つ。自動の名前は `{テーブル物理名}_ck{n}`(nはリスト内の位置。1始まり)。手動の名前は入力必須で、モデル内で重複できない(6.7-2)。検査式が空の場合は、生成前検証のエラー(9.5)。

### 6.5 トリガー
1. テーブルは複数のトリガーを持てる。プロパティペインにトリガーの一覧を表示し、追加ボタン、選択行の削除ボタン、ドラッグ&ドロップによる順の変更を提供する。行表示は、順、名前、タイミング、イベント。
2. トリガー1行の項目
   3. 本体の元: 「パブリック」(8.1の種別がトリガーのメソッドから選択)または「入力」(対象DBごとのタブに本体を直接入力する)。
   4. 名前: 名前の決め方(自動 / 手動)を選ぶ。自動は `{テーブル物理名}_trg{順(2桁ゼロ埋め)}`(順はリスト内の位置。1始まり)で、読み取り専用で表示する。手動は入力必須で、モデル内で重複できない。順が名前に入るのは、PostgreSQLが同じイベントのトリガーを名前の昇順に発火するため、並べ替えを発火順に反映させるため。
   5. タイミング: BEFORE / AFTER(既定BEFORE)
   6. イベント: INSERT / UPDATE / DELETE(複数選択、1つ以上。既定INSERT)
   7. 行単位: ROW / STATEMENT(既定ROW)
   8. 条件(WHEN): 任意の文字列 関数への引数: 任意の文字列(`EXECUTE FUNCTION 関数(引数)` の括弧の内側。例 `'80'`)。UPDATEの対象: 「テーブル全体」または「指定した列」(`UPDATE OF 列...`。実列と共通列から1列以上を選ぶ)。INSERT / DELETE のイベントと組み合わせられる(例 `INSERT OR UPDATE OF a, b`)。
9. 本体: パブリックの場合はメソッドの対象DB分の本体(8.1-3)、入力の場合は直接入力した対象DB分の本体を使う。本体の中の `{{table}}`(テーブル物理名)、`{{trigger}}`(トリガー名)は、アプリが生成用JSONの作成時に置換する。
10. 対象DB分の本体が空の場合は、生成前検証のエラー(9.5)。
11. ロック中のテーブルのトリガーは編集できない(5.3-2)。

### 6.6 ビュー
1. ビューはエンティティの一種で、ID、ロック、論理名、物理名、コメント、生成前実行クエリ、生成後実行クエリを持つ。ビューの列は読み取り専用。ビューのソースはテーブルのみ(ビューをソースにはできない)。
2. 種別は「結合ビュー」「関数ビュー」「SQLビュー」。追加時に定義ダイアログを開く。プロパティペインから「定義を編集」でも開く。
3. 結合ビューの定義
   4. ソース: テーブルを1つ以上選ぶ。各ソースにエイリアスを付ける(既定は物理名。重複する場合は連番)。最初のソースがFROMになる。
   5. 結合: 2つ目以降のソースごとに、結合種別(INNER / LEFT / RIGHT / FULL。既定INNER)と、結合条件(左のソースの列と、このソースの列の組。複数の組はANDで結ぶ)を指定する。ソースを追加したとき、既存のリレーションシップから結合条件の初期値を自動提案する(親列と子列の対応)。提案は編集できる。
   6. 出力列: ソースの列(実列と共通列)から選ぶ。出力列名(別名)を指定できる(既定は元の列の物理名)。論理名も指定できる。出力列名はビュー内で重複できない。
   7. WHERE: 任意の文字列(内容は検証しない)。
8. 関数ビューの定義
   9. メソッド: 種別がファンクションの登録メソッド(8.1)から1つ選ぶ。
   10. 引数: 文字列のリスト(式として、そのまま出力する)。
   11. 戻り列: 列名と型(パラメータを含む)を手入力する(1つ以上)。
   12. 出力は `SELECT * FROM <メソッドの名前>(引数)` の形(DB差異の吸収はポストファイル)。
13. 表示: テーブルと同じ形(ヘッダ + 列行)で、ヘッダの色を別色(設定の「ビューのヘッダ背景色」)にし、ヘッダに「VIEW」を表示する。列行にはPK・NotNull・デフォルトのマークを表示しない。ビューからソースのテーブルへ、薄い点線(選択できない)で依存線を表示する。
14. ビューはリレーションシップの端点にできない。
15. ビューのソースになっているテーブルは削除できない(6.1-12-3)。ビューが使っている列は削除できない(6.2-7-3)。
16. 出力の順序はテーブルの後(9.6-2)。
17. 定義の不備(ソースが0、出力列が0、関数が未選択、SQLビューのSQLが空、出力列名の重複、結合条件の不備)は、生成前検証のエラー(9.5)。
18. SQLビューの定義: SELECT文(複数行テキスト)と、キャンバスへの表示用の列(列名、論理名、型。任意)を持つ。出力は `CREATE VIEW <物理名> AS <SELECT文>` の形で、SELECT文の内容は検証しない。コメントは `COMMENT ON VIEW` で出力する。ソースや結合の定義は持たない。

### 6.7 名称の入力規則
1. 物理名: 必須。形式は設定(10.2)の「物理名の形式」(正規表現。既定 `^[A-Za-z_][A-Za-z0-9_]*$`)に一致すること。
2. 物理名の重複禁止(大文字小文字を区別しない)の範囲は次のとおり。
   3. エンティティの物理名(テーブルとビューの全体)
   4. 同じテーブル内の列の物理名(実列と、展開される共通列を含む。共通列の衝突は8.2-3)
   5. 制約名(インデックス、ユニーク、外部キー、トリガー)のモデル全体
   6. メソッド名(ファンクションとトリガーの全体)
   7. ダイアグラム名
8. 論理名: 任意。重複できる。
9. 入力時に検証し、不正な値は赤枠で示して確定しない(3.6-5)。
10. 識別子の長さと予約語は、生成前検証(9.5)で警告する。
11. 他のオブジェクトからの参照はIDで持つので、物理名を変更しても参照は壊れない。

## 7. リレーションシップ
1. リレーションシップは、テーブルとテーブルの関係を表すERオブジェクト(ID、ロックを持つ)。ビューは端点にできない。自己参照(親と子が同じテーブル)を許可する。自己参照のリレーションシップは、依存関係を無効にして作成し、子の外部キー列は親の鍵の列とは別の列にする(7-5)。同じ2つのテーブルの間に複数のリレーションシップを持てる。
2. 表示: IE記法で、2つのテーブルの矩形の中心同士を結ぶ直線を、各矩形の境界で切って描く(直線)。テーブルの移動に追随する。選択はクリック(線から6px以内)。ロック中は中点にロックアイコンを表示する。終端の記号は次のとおり。 自己参照は、矩形の右辺から右へ出て同じ辺へ戻る折れ線で描く(同じテーブルに複数あるときは下へずらす)。
   3. 親側: 依存関係が有効(親が必須)なら縦棒1本(`|`)、無効(親が任意)なら丸+縦棒(`o|`)。
   4. 子側: 子側多重度が1なら縦棒(`|`)、多なら丸+カラスの足(`o<`)。
5. 追加の前提と親子の初期値
   6. 追加の有効条件は4.2-5。
   7. 親と子の初期値は、IDが小さい方を親とする。プロパティの「方向」の入替で、親と子を入れ替えられる(入れ替えたときは、7-5の列対応の決定をやり直す)。
8. プロパティ(プロパティペイン)。上段にリレーションシップ自身の項目、続けて親テーブル、子テーブルのプロパティ(6.1-9)を表示する(各テーブルのロックに従う)。
   9. 方向: 親テーブルと子テーブルの名前。入替ボタン。
   10. 列対応: 親の列と子の列の組の一覧(順に対応する)。親側の候補は、親の主キー列(既定は全主キー列)、または親の任意のユニーク制約の列(共通列を含む)。子側は、子の実列または共通列から、ユーザーが自由に選べる。組の数は親の鍵の列数と同じ。
   11. 依存関係: 有効 / 無効(7-6)。
   12. 子側多重度: 1 / 多(既定は多)。表示のみで、SQLにUNIQUEは付与しない。
   13. 外部キー制約名: 名前の決め方(自動 / 手動)。自動は `{子テーブル物理名}_fk{n}`(nは、そのテーブルを子とするリレーションシップをID昇順に並べたときの位置。1始まり)。手動は入力必須で、モデル内で重複できない。
   14. ON DELETE と ON UPDATE: 「適用しない」(句を出力しない)/ NO ACTION / RESTRICT / CASCADE / SET NULL / SET DEFAULT。既定はどちらもNO ACTION。子の外部キー列のいずれかがNotNullまたはPKのとき、SET NULLは選択できない。依存関係の有効/無効にかかわらず設定できる。
   15. ロック(5.3)。遅延可否(DEFERRABLE): 「指定しない」/ DEFERRABLE INITIALLY IMMEDIATE / DEFERRABLE INITIALLY DEFERRED(既定は指定しない)。依存関係の連動(7-6)とは無関係。
16. 追加時の外部キー列の決定: 親の鍵の列Pごとに、子テーブルの実列から次の順に探す。列のドラッグ(3.4-9)で追加するときは、ドラッグ元の列に対応する子の列を、ドロップした列に固定し、ほかの列だけを次の順で決める。
   17. 物理名がPの物理名と同じ列(大文字小文字を区別しない)。
   18. 物理名にPの物理名を含む列(部分一致、大文字小文字を区別しない)。
   19. 同じ順位の候補が複数あるときは、列順で先頭のもの。同じ親テーブルとの別のリレーションシップに割り当て済みの列は候補にしない。 自己参照では、親の鍵の列自身は候補にしない。
   20. 見つからない場合は、子に新しい列を作る。物理名は `{親テーブル物理名}_{P物理名}`(重複する場合は末尾に `_2`、`_3` ...)、論理名は `{親テーブル論理名}_{P論理名}`、型はPと同じ(`auto` は `integer`。長さなどのパラメータは継承する)、NotNullは依存関係が有効なら有効、無効なら無効、挿入位置は依存関係が有効なら子のPK列の直後、無効なら末尾。
   21. 自動で決めた後も、ユーザーは列対応の子列を既存の任意の列へ変更できる。自動作成された列は、割当を変更しても残る(不要なら削除する)。
   22. 子の列の型が親の列と異なる場合は、警告を表示する(確定はできる)。
23. 依存関係
   24. 有効: 識別関係。子の外部キー列を子の主キーに含め、NotNullにする。
   25. 無効: 外部キー列を子の主キーに含めず、Null許可にする。
   26. 例外: ON DELETEとON UPDATEの両方が「適用しない」(参照規則を適用しない)ときは、依存関係が有効でも、子の主キーには含めない(NotNullは維持)。
   27. 連動の実行: 次の変更の時点に限り、子の外部キー列のPKとNotNullを連動して変更する。変更の前に確認ダイアログ(はい / いいえ。いいえでその変更を取り消す)を表示する。以後、ユーザーが列のプロパティで個別に変更した値は上書きしない。
      1. 依存関係を有効にした(参照規則は適用する): PKとNotNullを有効にする。
      2. 依存関係を無効にした: PKとNotNullを解除する。
      3. 依存関係が有効のまま、ON DELETEとON UPDATEの両方を「適用しない」にした: PKを解除する(NotNullは維持)。
      4. 依存関係が有効のまま、どちらかを「適用しない」以外に戻した: PKを有効にする。
   28. 子の列が共通列(仮想列)の場合は、PK・NotNullを連動して変更しない。
29. 削除: リレーションシップの削除で、外部キー列は残る(PK・NotNullの状態も維持)。確認は不要(Undoできる)。
30. 端点のテーブルの削除、列の削除の影響は、6.1-12、6.2-7。
31. ロックの影響は5.3-2。
32. 共通列への参照: 列対応の親の列(ユニーク制約を通じて)と子の列に、共通列を指定できる。展開されない共通列への参照は、生成前検証のエラー(8.2-5)。

## 8. 共有リソース

### 8.1 メソッド
1. メソッドはモデルの共有リソース。ERオブジェクトではなく、ID・名前・属性だけを持つ(ロックは持たない)。種別は「ファンクション」「トリガー」。
2. 管理ダイアログ(操作メニューの「メソッド管理」、およびメソッドの選択欄の「…」から開く): 左に、種別のタブ(ファンクション / トリガー)と一覧(追加、選択行の削除)、右にプロパティを表示する。
3. プロパティ ほかに、コメント(`COMMENT ON FUNCTION` で出力)、引数の定義(`COMMENT ON FUNCTION 名前(引数)` の括弧の内側)、依存テーブル・ビュー(ファンクションのみ。8.1-14)、スキーマ(空のときはモデルのスキーマ。外部定義には付けない)を持つ。
   4. 名前: 必須。モデル内で重複できない(6.7)。
   5. 外部定義(ファンクションのみ): 有効のとき、定義(CREATE文)を出力しない。`now()` のような組込み関数の登録に使う。
   6. 対象DB(postgresql / mysql / sqlserver / sqlite)ごとのタブに、次を入力する。
      1. 呼出し式(ファンクションのみ): デフォルトのメソッド(6.2-4)と関数ビュー(6.6)で使う式。省略したときは `{名前}()`。
      2. 本体: ファンクションは定義のCREATE文、トリガーはトリガーの本体(複数行テキスト)。
7. 生成では、対象DBのタブの内容だけを使う。
8. 本体が空の扱い
   9. 外部定義のファンクション: 本体は不要。呼出し式が空なら `{名前}()` を使い、エラーにしない。
   10. 外部定義でないファンクション、およびトリガー: 対象DBの本体が空で、どこかから参照されている場合は、生成前検証のエラー(9.5)。参照されていない場合は、出力せず、警告もしない。
   11. 本体があり外部定義でないメソッドは、参照の有無にかかわらず出力する。
12. 削除: 参照しているエンティティと列(またはトリガー)の一覧を警告として表示する。確認後に、参照を解除し(列のデフォルトは「なし」、トリガー行は削除)、1コマンドで削除する。関数ビューが参照している場合は、削除できない(先にビューの修正を促す)。ロック中のエンティティが参照している場合は、削除できない(5.3-2-4)。
13. 参照元は、列のデフォルト(6.2-4)、テーブルのトリガー(6.5)、関数ビュー(6.6)。
14. 依存テーブル・ビュー: ファンクションは、依存するテーブルとビューを複数選べる。アプリは、依存先のうち最後に作成されるものの直後に、そのファンクションを出力する(ビューへの依存があれば、そのビューの直後。ビューはテーブルの後に作成される)。依存先のないファンクションは、テーブルより前に出力する(9.6-7)。依存先をモデルから削除すると、依存から外れる。ファンクションの本体(対象DB分)が別のファンクションを呼んでいる(名前 + `(` が本体に現れる)場合は、呼出し先より後に出力する(`LANGUAGE sql` は作成時に本体が検査されるため)。呼出し先の出力位置が依存先の直後なら、呼ぶ側も同じかそれより後の位置にする。循環しているときは、登録順で打ち切る。
15. 標準メソッド: 新規のモデルは、外部定義のファンクション「空文字」(名前 `empty_string`、呼出し式 `''`)を持つ。空文字のデフォルトに使う(6.2-4)。

### 8.2 共通列パターン
1. 共通列パターンはモデルの共有リソース。次を持つ。
   2. ID、名前(必須、モデル内で重複できない)
   3. 有効 / 無効
   4. 対象フィルタ: テーブルの物理名に全体一致する正規表現
   5. 除外フィルタ: 同じく正規表現(任意)
   6. 位置: 先頭 / 末尾
   7. 列のリスト: 6.2の項目のうちPKを除いたもの(論理名、物理名、型とパラメータ、Null許可、デフォルト、コメント)。各列はモデル内で一意のIDを持つ。
8. 管理ダイアログ(操作メニューの「共通列パターン管理」): 一覧(追加、削除、ドラッグ&ドロップで順の変更)とプロパティ。正規表現の試験欄に、テーブル物理名を入力して一致/不一致を確認でき、現在のモデルで一致するテーブルの一覧(件数)も表示する。
9. 適用の規則: 有効なパターンのうち、テーブルの物理名が対象フィルタに全体一致(大文字小文字を区別する)し、除外フィルタに全体一致しないものを、パターンの並び順で適用する。位置が「先頭」の列は実列の前に、「末尾」の列は実列の後に、パターンの並び順に並べる。パターンの列の物理名が、実列、または先に適用されたパターンの列と重複する場合は、先に存在する方を優先し、後の列は展開しない(生成前検証で警告。9.5)。
10. 仮想列: 共通列はテーブルに保存せず、展開結果をアプリ全体で共通に使う。パターンを変更すると、すべてのテーブルに追従する。
   11. 表示: 薄色・斜体の読み取り専用行(6.1-5)。PKにはならない。
   12. 参照できる箇所: 制約(インデックス、ユニーク)の列、リレーションシップの列対応(7-10)、ビューの出力列と結合条件(6.6)、生成前検証(9.5)。参照は列のIDで保持する。
   13. 生成用JSONでは、展開済みの列として出力する(`origin: "common"`。付録B)。
14. 参照の維持: 展開結果に含まれなくなった共通列(パターンの無効化、フィルタの変更などによる)への参照は、削除せず保持し、生成前検証でエラーにする(「共通列 X がテーブル Y に展開されない」)。パターンの列そのものを削除する場合の影響は、実列の削除(6.2-7)と同じ規則で扱う。
15. 不正な正規表現: そのパターンを無効扱いにし、赤表示する。有効なパターンに不正な正規表現が残っていると、生成前検証のエラー(9.5)。
16. パターンは `.pero` に保存する(付録A)。

## 9. 機能

### 9.1 Undo / Redo
1. モデル、ダイアグラム、共有リソースに対するすべての変更を、Command(execute / undo)として実装する。
2. 履歴の上限は設定(10.2。既定100)。超えたときは古いものから破棄する。
3. 1コマンドの粒度
   4. ドラッグ移動(複数選択の同時移動を含む)は1コマンド。
   5. テキストなどの入力は、確定(Enterまたはフォーカス喪失)ごとに1コマンド。
   6. ダイアログのOKは1コマンド。
   7. リレーションシップの追加(外部キー列の自動作成を含む)は1コマンド。
   8. 依存関係などの変更に伴う連動(7-6)は、変更と合わせて1コマンド。
   9. 「モデルから削除」は、巻き込まれる削除を含めて1コマンド。
10. 新規作成、ファイルを開くで履歴をクリアする。保存では履歴を維持し、保存した時点の履歴の位置を記録する(未保存の判定は4.1-8)。
11. Undoの対象外: 設定の変更、ズームとスクロール、選択の変更。
12. コマンドはシリアライズできる形(種別と引数のJSON)で実装する。キャッシュ(9.2)がこれを記録する。

### 9.2 キャッシュ(異常終了からの復旧)
1. 目的は、異常終了からの復旧。保存先は `%LOCALAPPDATA%\PERO\cache\`。編集中のモデルは常に1つなので、1セットだけ持つ。
   2. `meta.json`: モデルID、ファイルパス、保存済みかどうか(`savedOnce`)、アプリのバージョン。
   3. `base.pero`: 最後に保存した(または開いた)時点の内容。
   4. `commands.jsonl`: それ以降の操作の記録(1行1件)。
5. 記録
   6. 変更の都度、実行したコマンド、Undo、Redoを1行ずつ `commands.jsonl` に追記する(差分の記録)。
   7. 保存に成功したとき、`base.pero` を保存した内容で更新し、`commands.jsonl` を空にする。
   8. 一度も保存していない新規のモデルは記録しない(復旧の対象外)。最初の保存の後から記録を始める。
9. 異常終了の検知: 起動処理の最後にセッションロックファイル `session.lock` を作り、正常終了の処理で削除する。起動時に `session.lock` が残っていれば、前回は異常終了したと判定する。
10. 起動と終了の手順
   11. 起動: (1) `session.lock` を確認する。(2) 前回異常終了していて、かつ、キャッシュに `savedOnce` が真で `commands.jsonl` が1行以上あるときは、復元確認ダイアログ「前回は異常終了しました。編集中の内容を復元しますか?」(はい / いいえ)を表示する。(3) はい: `base.pero` に `commands.jsonl` を順に再生して復元し、整合性確認(9.4)を行い、未保存の状態で開く(ファイルパスは `meta.json` のもの)。いいえ: 何もしない。(4) 復元の可否が確定した後に、キャッシュを削除する。(5) `session.lock` を作る。(6) 通常どおり起動する。
   12. 正常終了: 設定の保存、キャッシュの削除、`session.lock` の削除を行う。
13. データファイルの異常: ファイルを開いたときの整合性確認が修復できなかった場合(9.4-6)、同じファイルのキャッシュ(`meta.json` のファイルパスが一致し、`savedOnce` が真)があれば、復元を提案する(4.と同じダイアログ)。なければ、バックアップが有効で該当ファイルのバックアップがあるときは、最新のバックアップからの復元を提案する(はい / いいえ)。どちらもない場合は、エラーを表示する。
14. キャッシュの破損、再生の失敗: 復元せずに通常どおり起動し、キャッシュを削除してエラーをログに記録する。

### 9.3 バックアップ
1. 設定(10.2)でバックアップが有効なとき、サイクルタイム(既定5分)ごとに、前回のバックアップ以降に変更があれば、編集中のモデルをバックアップする。保存済みのファイルが対象で、一度も保存していない新規のモデルは対象外。
2. 内容は、現在のメモリ上のモデルを `.pero` 形式で出力したもの(キャッシュの差分を統合した状態と同じ)。
3. ファイル名は `{ファイル名(拡張子なし)}_{yyyyMMdd_HHmmss}.pero`。フォルダは設定による(既定は `%LOCALAPPDATA%\PERO\backup`)。
4. 保存期間(既定5日)を超えたバックアップは、起動時と各バックアップの実行時に削除する。
5. バックアップに失敗しても編集を妨げない。ステータスバーに通知し、ログに記録する。
6. 設定の変更は、次のサイクルから反映する。

### 9.4 データ整合性確認
1. ファイルを開いたとき(読込の直後)と、保存するとき(書込みの直前)に行う。
2. 確認の内容は、JSONの構成、キーの有無、値の有効性、参照の有効性。
3. 検査と処理(上から順)
   4. JSONの構文エラー: 修復できない(9.2-5へ)。
   5. `formatVersion`: 欠落は1とみなす。現行より古い場合はマイグレーションする。現行より新しい場合は警告して開かない。 現行より古い形式(1、2)のファイルは、後から加わったキーの欠落を修復として記録せず既定値にし、標準型 `interval`、`varchar_nolen` を補う(現行は3)。
   6. 必須キーの欠落、型の不一致、値域外(列挙外、範囲外、不正なID): 標準(付録Aの既定値)に置き換える。標準に置き換えられないキー(ID、参照先など)は、その項目を削除する。
   7. 未知のキー: 無視する(保持して、保存時に書き戻す)。
   8. 参照切れ(存在しないエンティティ、列のID、型、メソッド、配置されたエンティティ)とIDの重複: 該当する要素を削除する。ただし、共通列への参照は、パターンの列のIDが存在する限り削除しない(8.2-5)。
   9. 型の不足: 標準型(付録C)が不足していれば補う。
10. 3.のうち3、5、6の修復を行ったら再度検査する(最大3回)。
11. 修復を行ったときは、修復内容(件数と概要)をダイアログに表示し、ログに記録する。ファイルを開いたときは、元のファイルを `{ファイル名}.pero.bak` にコピーして退避する(既存の `.bak` は上書きする)。保存のときは、修復した後の内容を保存する。
12. 3回の再検査の後も異常が残る場合は修復できない。開くときはエラーを表示し、復元を提案する(9.2-5)。保存するときは保存を中止し、エラーを表示してログに記録する(メモリ上のデータは保持する)。

### 9.5 生成前検証
生成実行(9.6)とJSON出力(9.7)の前に行う。エラーが1つでもあれば中止し、一覧を表示する。警告は、生成を続行して結果ダイアログに表示する。
1. エラー
   2. 物理名が空、または形式不正(エンティティ、列、制約、メソッド)
   3. 物理名の重複(6.7-2の範囲)
   4. 列が使う型が存在しない、または対象DBの物理名テンプレートが未定義
   5. 参照切れ(メソッド、共通列、列、エンティティ)。展開されない共通列への参照を含む(8.2-5)
   6. 参照されているメソッドで、外部定義でなく、対象DBの本体が空(8.1-5)
   7. リレーションシップの列対応: 数の不一致、未割当、親の列が主キーでもユニーク制約でもない
   8. ビュー定義の不備(6.6-9)(SQLビューのSQLが空を含む)
   9. 有効な共通列パターンの正規表現が不正
   10. 1つのテーブルに `auto` 型の列が2つ以上。CHECK制約の式が空。デフォルトの式が空。ユーザー定義型の不備(複合型の項目が0、列挙型の値が0、型の名前が形式不正)。スキーマ名が形式不正。メソッドの依存テーブルが存在しない。
   11. トリガーの不備(イベントが未選択、名前の重複、対象DBの本体が空)
12. 警告
   13. 主キーのないテーブル
   14. 外部キー列と親の列の型の不一致
   15. 共通列の物理名の衝突(後の列が展開されない。8.2-3)
   16. 識別子の長さの超過(postgresqlは63、mysqlは64、sqlserverは128、sqliteは制限なし)
   17. 予約語(postgresqlのみ。アプリ内蔵のリスト。他のDBは対象外)
   18. 列が0のテーブル
   19. ON DELETEまたはON UPDATEがSET DEFAULTで、子の列にデフォルトがない
   20. 出力にスキーマを含めるが、モデルのスキーマが空。UPDATE列を指定したトリガーにUPDATEのイベントがない。

### 9.6 生成実行
1. 手順(RUN > 生成実行)
   2. ポストファイルの確認: モデルのポストファイルのパスが空のときは、ポストフォルダの一覧(9.10-1)から、モデルの対象DBのポストファイル(なければ先頭)を使い、そのパスをモデルのプロパティに保存する(コマンド)。一覧に使えるものがないときだけ、ファイルを開くダイアログ(フィルタ `*.post`、既定のフォルダは設定のポストファイルのフォルダ)で選ばせる(キャンセルしたら中止する)。指定されたポストファイルを、生成が終わるまでロックし(排他。ほかの操作から、書込み・削除・名前の変更ができない)、終わったら解除する。ポストファイルが存在しないとき(ロックできないときを含む)は、エラーを表示して処理を停止する。ファイルの先頭10行以内の `// @post` 行(9.6-4)を読み、`apiVersion` が合わなければエラー。生成に適用するデータベースは、メタ情報の `targetDb`(設定で関連付けた種類を含む。9.10-2)で決める。モデルの対象DBと違うときは、モデルの対象DBをポストファイルの種類に変更し(コマンド。Undoできる)、ステータスバーに通知する。`targetDb` が既存の種類でなく、関連付けもないときは、エラーを表示して処理を停止する。
   3. 生成前検証(9.5)。エラーがあれば中止する。
   4. 生成用JSON(付録B)を作り、`PostRunner` で `main(jsonText)` を実行する(別Isolate。タイムアウトは設定による)。例外、タイムアウト、戻り値が文字列でないときは、エラーダイアログ(メッセージとスタック)を表示してログに記録する。
   5. 出力先: `{出力フォルダ}\{出力ファイル名}.{拡張子}`。出力フォルダが空のときは `.pero` と同じフォルダ、それも無い(未保存)ときはマイドキュメント。出力ファイル名が空のときは `.pero` のファイル名(未保存なら「無題」)。拡張子は設定による。保存先は、ファイルの保存ダイアログで選ぶ(既定のフォルダとファイル名は、この出力先の規則による。まだ存在しないファイルも指定できる。既存のファイルへの上書きの確認は、保存ダイアログが行う)。キャンセルしたときは、ファイルを書かず、ステータスバーに通知する。UTF-8(BOMなし)で書き、改行は設定(既定CRLF)に変換する。 改行コードの変換は、引用符(シングルクォート)で囲んだ文字列リテラルの中には適用しない(コメントなどの内容を変えないため)。ファンクション・ビューの本体、コメント(`--`、`/* */`)の改行など、それ以外は設定の改行コードに変換する。引用符が閉じていないなど解析できないときは、全体を変換する。
   6. 結果ダイアログ: 成功、警告の一覧、出力ファイルのパスを表示し、「ファイルを開く」「フォルダを開く」ボタンを置く。実行中の表示: 生成実行の操作(ボタン、F5)の直後から、画面全体を覆うオーバーレイと、ローディング(くるくる)とメッセージ「生成しています…」を表示し、操作できなくする。生成前検証と生成用JSONの作成は別Isolateで行い、画面を止めない。保存ダイアログが閉じる(キャンセルを含む)、または生成が終わるまで表示し、結果・エラーのダイアログを出す前に外す。表示中は、生成実行をもう一度行っても何もしない(ポストファイルのロックの衝突を防ぐ)。
7. 出力の構成と順序: アプリは付録Bの順序の情報を渡す。同梱の `postgresql.post` は次の順に出力する。
   8. 開始クエリ
   9. スキーマ(`CREATE SCHEMA IF NOT EXISTS`。出力にスキーマを含めるとき)→ ユーザー定義型(`CREATE TYPE`)→ ファンクション(定義の本体があり、外部定義でないもの。依存テーブル・ビューのあるものは、最後に作られる依存先の直後)
   10. テーブル(依存順。各テーブル: 生成前クエリ、CREATE TABLE、インデックスとユニーク、生成後クエリ)
   11. 外部キー(後付けのものを含む)(遅延可否があるときは `DEFERRABLE ...` を付ける)
   12. ビュー(各ビュー: 生成前クエリ、CREATE VIEW、生成後クエリ)(SQLビューは `CREATE VIEW 名前 AS <SQL>`)
   13. トリガー
   14. 終了クエリ
15. 依存順: アプリが `tables` を親から子の順(トポロジカル順)に並べる。循環がある場合は、循環を構成する外部キーに `deferred: true` を付ける。ポストファイルは、`deferred` の外部キーを、すべてのテーブルを作成した後にALTER TABLEで出力する。`deferred` でない外部キーは、親が先に出力済みなので、CREATE TABLEの中でも後でもよい。
16. ポストファイルの契約
   17. JavaScript(ES2020)、UTF-8、拡張子 `.post`。flutter_js(QuickJS)で実行する。
   18. `function main(jsonText)`: 引数は生成用JSONの文字列、戻り値は生成ファイル全文(文字列。改行は `\n`)。
   19. エラーは `throw` する。生成を中止し、メッセージを表示する。
   20. ファイル、ネットワーク、タイマーは使えない。`console.log` はログ(info)に記録する。
   21. 先頭10行以内に、次の形式のメタ情報を必ず書く: `// @post name=<表示名> targetDb=<dbKind> apiVersion=<整数> [role=<export|import>]`。`role` は役割(エクスポート用 / インポート用。0.2)で、省略時は `export`。`export` と `import` 以外の値は、メタ情報が不正として扱う
   22. 生成用JSONのスキーマは付録B。`apiVersion` は現在3。付録Bを変更するときは `apiVersion` を上げる。
23. 同梱のポストファイルは `post\postgresql.post`(PostgreSQL用。既定)、`post\mysql.post`(MySQL 8.0用)、`post\sqlserver.post`(SQL Server 2016 SP1以降のT-SQL用)。MySQL・SQL Serverにない機能(ユーザー定義型、DEFERRABLE、トリガーのWHEN・UPDATE OF・BEFORE など)は、出力せず、`-- [PERO] ...` のコメントで残す。MySQLのトリガーはイベントごとに分け、SQL Serverのビュー・トリガー・ファンクションは `GO` で区切る。ポストファイルのフォルダと既定のファイルは設定による(10.2)。ポストフォルダは、ビルド時に実行ファイルと同じフォルダ内へコピーする。
24. 再実行用のDROP: 設定(10.2)の「再実行用のDROP文を付ける」が有効のとき、生成用JSONの `model.dropBeforeCreate` が真になり、ポストファイルは、ユーザー定義型・テーブル(`CASCADE`)・ビューの CREATE の前に `DROP ... IF EXISTS` を出力する。ファンクションは、本体を `CREATE OR REPLACE` で書くことで再実行できるため、DROPしない。
25. スキーマ: 出力にスキーマを含めるとき、生成用JSONの `schemas`、テーブルとビューの `schema`(エンティティのスキーマ。5.2-1)を使って、ポストファイルはテーブル名・ビュー名を `スキーマ.名前` で出力する(外部キーの両端、結合ビューのソースを含む)。ユーザー定義型の名前(`CREATE TYPE`、`DROP TYPE`、`COMMENT ON TYPE`、列とビューの戻り列の型)と、メソッド(トリガーの `EXECUTE FUNCTION`、関数ビューの `FROM`、`COMMENT ON FUNCTION`)にも、スキーマ(型・メソッドのスキーマ。空ならモデルのスキーマ)を付ける。外部定義のメソッドには付けない。ファンクションの定義の名前、制約・インデックスの名前にはスキーマを付けない(本体の記述に従う)。入力のトリガー(本体の元が「入力」)の呼出しにも付けない。

### 9.7 JSON出力
1. RUN > JSON出力は、生成用JSON(付録B)をファイルに書き込む。ポストファイルに渡すJSONそのもので、ポストファイルの確認や他ツールとの連携に使う。出力の前に生成前検証(9.5)を行い、エラーがあれば中止する。
2. 保存ダイアログの既定のフォルダは、既存ファイルを開いているときはそのフォルダ、無ければマイドキュメント。既定のファイル名は `{出力ファイル名}.json`。UTF-8、インデント2。
3. 保存用の `.pero`(付録A)とは別物。

### 9.8 画像出力
1. RUN > 画像出力は、現在のダイアグラムをPNGまたはPDFに出力する。
2. オプションダイアログ
   3. 形式: PNG / PDF
   4. 範囲: 「用紙ページごと」(PNGは1ページ=1ファイル、PDFは1ページ=PDFの1ページ)/「全体を1枚」(グリッド全体)
   5. 解像度(dpi): 既定は設定による。100〜600。
6. 保存先: PNG(用紙ページごと)はフォルダを選び、ファイル名は `{ダイアグラム名}_r{行}c{列}.png`。PNG(全体)とPDFは、ファイルの保存ダイアログで指定する。
7. ピクセル数は、論理px × dpi ÷ 96。1辺が16000pxを超える場合は、dpiを自動で下げて、警告を表示する。
8. 出力内容は、配置されたエンティティとリレーションシップ(画面と同じ見た目、現在のテーマ)。選択の強調、ページ境界線は含めない。

### 9.9 自動配置
1. 操作メニューの「自動配置」は、現在のダイアグラムに配置されたエンティティを対象とする(選択中のエンティティがあれば、選択分だけ)。
2. ロック中のエンティティは動かさない(障害物として扱い、重ならないように他を配置する)。
3. アルゴリズム
   4. 対象を、リレーションシップの親から子の向きで層に分ける(親を持たないものが層0、それ以外は親の最大の層 + 1。循環は切って次へ進む)。
   5. 層ごとに行を作り、層の中は物理名の昇順に並べる。
   6. 用紙ページの幅から余白(40px)を引いた幅で折り返しながら、左から右へ配置する。層の間とエンティティの間の間隔は、設定の「整列スペース」(既定40px)。
   7. 最初の用紙ページの左上から余白(40px)の位置を起点にする。選択分だけを対象にしたときは、選択範囲の外接矩形の左上を起点にする(対象外のエンティティとの重なりは避けない)。
   8. 実行後に、用紙ページを再計算する(5.2-4)。
9. 1コマンドで実行し、Undoできる。
10. 実行後は、配置した範囲の左上(余白を除く)へスクロールし、配置した件数をステータスバーに通知する。対象がないとき、失敗したときも、ステータスバーに通知する(ログに記録する)。

### 9.10 ポストファイルの種類(kind)
1. ポストファイルの一覧: ポストフォルダ(10.2)にある `*.post` を、起動時と設定の適用時に走査し、先頭10行以内のメタ情報(9.6-4)から、表示名、対象DB(`targetDb`)、`apiVersion` を読む。メタ情報がない、または `apiVersion` が合わないファイルは、使えないものとして扱う(一覧に出さない)。ポストフォルダに使えるポストファイルが1つもないときは、起動時に警告ダイアログを表示してアプリケーションを終了する(復元用のキャッシュは消さない)。設定の適用時は、終了せずにステータスバーに通知する。
2. 種類(kind)の決定: ポストファイルの種類は、メタ情報の `targetDb` が postgresql / mysql / sqlserver / sqlite のいずれかであればそれ。そうでない(ユーザーが作成した)ポストファイルは、設定の「種類(kind)の関連付け」(10.2。ファイル名またはメタ情報の `targetDb` の値から、既存の種類へ)で決める。関連付けは、メタ情報の種類より優先する。種類を決められないポストファイルは、一覧には出すが、生成では使えない(9.6-1-2)。
3. 表示の制限: ポストファイルがある種類だけを、対象のデータベースの候補、メソッド・型・トリガーの対象DBごとのタブ(8.1-3-6、6.3、6.5)に表示する。モデルが対象DBに使っている種類は、ポストファイルがなくても表示する。表示しない種類の入力済みの値は、保持する(削除しない)。使えるポストファイルが走査できていないときは、すべての種類を表示する。
4. 対象のデータベースを変更したときは、現在のポストファイルがその種類でなければ、その種類のポストファイル(ファイル名の昇順の先頭)へモデルのポストファイルを切り替える。ポストファイルを一覧から選んだときは、そのパスと種類をモデルに設定する(1コマンド)。
5. 役割(role): ポストファイルの一覧は、エクスポート用(`role=export`、省略時)とインポート用(`role=import`)に分けて扱う。エクスポート用だけが、対象のデータベースの候補、生成(9.6)、モデルのポストファイルの選択、起動時の「使えるポストファイルがない」の判定(1)に使われる。インポート用は、SQLインポートのダイアログ(9.11-2)の一覧にだけ使う。インポート用の `targetDb` は、データベースの種類の表示に使い、種類(kind)の関連付け(2)の対象にしない。

### 9.11 SQLインポート
1. 概要: SQL(DDL)を読み、モデルを作る、または現在のモデルへ追加する。SQLの解析は、インポート用ポストファイル(JavaScript。9.6-4)が行い、インポート結果(付録E)を返す。インポート結果からモデルへの変換は、アプリが行う(`lib/importer`)。データベースの違いは、インポート用ポストファイルで吸収する。同梱は `post\postgresql.import.post`(PostgreSQL用)。データベースへは接続しない(0.3-2)。
2. 操作: ファイルメニューの「SQLインポート」(4.1-27)で、ダイアログを開く。インポート用ポストファイルがないときは、置き場所と書き方を示して終了する。
   3. データベース: インポート用ポストファイルの一覧(9.10-5)から選ぶ。
   4. SQLファイル: 複数を選べる。上から順に読み、順序は変更できる。UTF-8(BOMは除く)。
   5. 取込先: 「新しいモデル」または「現在のモデルに追加」。新しいモデルは、未保存確認(4.1-8)の後、未保存の無題として開く(新規作成と同じ初期値。履歴をクリアし、キャッシュの対象外。9.2-2)。追加は、現在のダイアグラムへ配置し、1コマンド(`ImportSqlCommand`)でUndoできる(9.1-3)。
6. 実行: 選んだインポート用ポストファイルを、実行の間ロックし(9.6-1-2と同じ)、`main(jsonText)` を実行する(別Isolate。タイムアウトは設定による。10.2)。引数は `{ "files": [ { "name": ファイル名, "text": SQL全文 } ] }`、戻り値はインポート結果(付録E)。実行中は、画面全体のオーバーレイと、ローディングとメッセージ「SQLを取り込んでいます…」を表示し、操作できなくする(二重の実行もできない)。例外、タイムアウト、戻り値が不正なときは、エラーダイアログを表示してログに記録する(モデルは変更しない)。
7. 取り込む対象: テーブル(列、型、デフォルト、主キー、ユニーク、インデックス、CHECK制約、外部キー)、関数(ファンクション、トリガー関数)、ビュー、トリガー、ユーザー定義型(複合型、列挙型)、コメント。`tool/sql_to_pero.dart`(11.9)と同じ規則で変換する。
8. SELECT: コマンドではないSELECT(FROM句のある単独のSELECTまたはWITH)は、SQLビュー(6.6-9)に変換する。名前は `import_XX`(XXは連番。1から始め、10未満は2桁にそろえる)。取込先に同じ名前があるときは、次の空き番号にする。FROM句のないSELECT(関数の呼出し、定数など)はコマンドとみなし、解析できないものに分類する。
9. データの操作(INSERT / UPDATE / DELETE)と、そのほか取り込む対象でない文(DO、SET、GRANT、DROP、CREATE ROLE など)は、解析できないものに分類する。
10. 解析できないもの: 次のとおり扱う。
    11. ログ: 種類、理由、場所(ファイル名:行)を警告(warn)で、文の全文をデバッグ(debug)で記録する(11.5)。
    12. 結果ダイアログ: 件数、補足(自動追加した型など)、解析できないものの一覧を表示し、「取り込めなかった文を保存」で、別ファイルへ保存できる。保存するファイルは、各文を、種類・理由・場所のコメントと文の全文で並べたSQL(UTF-8)とする。
    13. 解析できなかった文は、モデルには残さない。
14. 変換の規則
    15. 型: PostgreSQL互換の型名を標準型(付録C)へ対応づける(serial 系は `auto`、長さなしの varchar は `varchar_nolen`)。対応のない型はカスタム型を追加する。ユーザー定義型は、同じ入力の中の CREATE TYPE と対応づける。インポート結果の列が `typeId` を持つときは、それを使う(付録E)。
    16. デフォルト: 空文字は標準メソッド「空文字」(8.1-15)、`now()` のような引数なしの関数呼出しは外部定義のメソッド(自動で登録。呼出し式はそのまま)、数値・真偽値・文字列は値、それ以外は式とする(6.2-4)。`auto` の列はデフォルトなし。
    17. 外部キー: 親の列の指定がないときは、親の主キー。子の外部キー列が子の主キーの全列のとき、依存関係を有効にする(自己参照は無効。7-1)。ON DELETE / ON UPDATE / 遅延可否(7-4)を取り込む。制約名は手動名とする。
    18. ファンクションの依存テーブル・ビュー: 本体(戻り値の型を含む)にテーブル名・ビュー名が現れるものを依存先にする(8.1-14)。取り込んだものだけでなく、取込先のモデルに既にあるテーブル・ビューも対象にする。
    22. 関数のコメント: COMMENT ON FUNCTION が引数を省略しているときは、CREATE FUNCTION の引数(既定値と OUT 引数を除く)を、メソッドの引数の定義(8.1-3)にする。
    19. 同名: 取込先に同じ物理名のテーブル・ビュー・メソッド、同名の型があるときは、取り込まず、解析できないものに分類する。
    20. スキーマ: 新しいモデルで、取り込んだ要素のスキーマが1種類だけのときは、モデルのスキーマにして、出力にスキーマを含める(5.1-2)。
    21. 配置: 取り込んだエンティティを、自動配置(9.9)で並べる。追加のときは、既存の配置の下から始める。

### 9.12 ポストファイルの書き方の支援
1. 共通ヘルパ: ポストフォルダ(10.2)に `pero.lib.js` があれば、アプリは、エクスポート用、インポート用を問わず、ポストファイルの前に読み込む(同じスコープ。名前空間 `pero`)。ポストファイルは、ヘルパを使わなくてもよい(同梱の `postgresql.post`、`mysql.post`、`sqlserver.post` は使わない)。同梱の `postgresql.import.post` は使う。ヘルパが無いときは読み込まず、ポストファイルがヘルパを使っていれば、実行時にエラーになる。
   2. 共通: `pero.stripTrailing`、`pero.endSemi`。
   3. エクスポート用: `pero.dialect(opts)`(識別子の引用、スキーマ付きの名前、文字列リテラル)、`pero.Output()`(文を空行で区切って組み立てる)、`pero.defaultSql(column, dialect)`(列のデフォルトのSQL式)。
   4. インポート用: `pero.splitSql`(SQLを文に分ける)、`pero.splitTop`、`pero.parenBody`、`pero.ident`、`pero.identParts`、`pero.sqlString`、`pero.ImportResult`(インポート結果の組立。`add`、`unparsed`、`nextViewName`、`toJson`)。
5. ひな形: `post\template\export.post`(エクスポート用)と `post\template\import.post`(インポート用)。ポストフォルダの直下ではないため、一覧には出ない。コピーして名前とメタ情報を書き換えて使う。そのまま動く最小限の内容とする。
6. ガイド: `doc/contents/ポストファイルの書き方.md` に、契約(9.6-4)、メタ情報、エクスポート用とインポート用の書き方、入出力JSON(付録B、付録E)の要点、共通ヘルパの一覧と使用例、デバッグの方法(`console.log` はログ、JSON出力 9.7)、よくある失敗を書く。

## 10. 設定

### 10.1 設定ファイル
1. 設定ファイル `settings.json` は、実行ファイルと同じフォルダ直下に保存する。そこに書き込めない場合(Program Files配下など)は、`%APPDATA%\PERO\settings.json` に保存し、ステータスバーに通知する。読込は両方を探し、実行ファイル直下を優先する。
2. 保存の契機: 設定画面のOKまたは適用で、すぐに保存する(一時ファイルに書いてからリネーム)。ウィンドウの位置・サイズ・最大化状態、分割割合、前回使ったフォルダ、最近使ったファイルは、変更の都度メモリに保持し、アプリケーションの正常終了時に保存する。
3. `settingsVersion` を持つ。破損、または読込に失敗したときは、既定値で起動し、壊れたファイルを `settings.json.broken` に退避して、ステータスバーに通知しログに記録する。
4. 設定の保存に失敗しても、動作は継続する(通知する)。
5. 全項目を既定値に戻せる(3.8-2)。

## 11. 規則

### 11.1 ディレクトリ・ファイル
1. 生成結果のレポートは、`doc/log` ディレクトリに、ファイル名 `yyyyMMdd_NNNN.md`(NNNNは4桁ゼロ埋めの番号)として保存する。レポートには次を含める。
   2. 実施した内容
   3. 項番(0.1-1)ごとの実装状況(済/一部/未/仕様差異)の表
   4. 付録D以外で、新たに仮定を置いた事項の一覧
   5. 「仕様未定義」(0.1-3)の一覧
   6. 同じ年月日、同じ番号に対する追加変更は、`yyyyMMdd_NNNN_add_M.md`(Mは1からの連番)として保存する。
7. 使い方やヘルプなど、使用にかかわるドキュメントは `doc/contents` に保存する。
8. 最終的にこの `CLAUDE.md` へ統合される追加、変更の指示は、`issue` ディレクトリに `yyyyMMdd_NNNN.md` として保存する。
   9. つまり「生成結果のレポート」と連動する。
   10. `CLAUDE.md` への統合も指示に含める。統合時、削除指示がない限り、`issue` ディレクトリと `doc/log` ディレクトリの中を削除しない。`CLAUDE.md` には、変更、追加、削除であることを記録しない(生成時に `issue` ディレクトリと `doc/log` ディレクトリを参照するため)。
11. `lib/` 以下は、細分化した機能別のディレクトリに分け、2階層を限度(`lib/xxx/xxx`)とする。細分化の程度は、2階層になる程度の抽象度とする。
   12. 細分化する機能が少ない(5以下)ときは、1階層でよい(`lib/xxx`)。
   13. 機能の分け方の目安: `model`、`command`、`persistence`、`generation`、`canvas`、`panel`、`dialog`、`settings`、`logging`、`common`。`model`、`command`、`persistence`、`generation` はFlutterに依存しない。

### 11.2 命名規則
1. ファイル名、クラス名などの名前付けは、Flutterの規則、慣例に従う。
2. クラス名は、デザインパターンがわかる、または意味が通る英語の名詞とする。ただし、「はい/いいえ」を表す `isXxxx` などの `is/as/has` の慣例を優先する。
   3. `Command` など、デザインパターンだけの名前では誤解や衝突を招くため、機能や動きを名詞にしたものと組み合わせる。
4. プリフィクスにアプリ名(`Pero` など)をつけない。

### 11.3 バレルファイル
1. 機能(11.1-4のディレクトリ)ごとにバレルファイル `lib/<機能>/<機能>.dart` を置き、ほかの機能からはバレルファイルだけを読み込む。

### 11.4 シリアライズ
1. `.pero` の保存と復元(付録A)のシリアライズと、ログ用の診断ダンプ(`toLogMap()`)は別の実装にする。`.pero` のシリアライズは、スキーマ(付録A)を明示的に定義して実装する。診断ダンプは、エラー追跡のためであり、復元には使用しない。

### 11.5 ログ
1. ログの出力先は `%LOCALAPPDATA%\PERO\logs\pero_yyyyMMdd.log`。レベルと保持日数は設定による(10.2)。
2. 記録する内容: 例外、ファイルの読み書き、整合性確認の修復(9.4-5)、生成の結果、ポストファイルの `console.log`(info)。
3. ロガーはRiverpodから提供され、アプリケーション全体をとおして同じ仕様のログ出力を行う。エラーが発生した機能を切り分けられるように、機能(11.1-4のディレクトリ)の名前をロガー名にする。

### 11.6 GoFデザインパターン
1. クラス名やファイル名にデザインパターンを含めない場合は、コメントに該当するパターン名を追加する。
2. 必ずしもデザインパターンに割り当てる必要はない。

### 11.7 テスト
1. `test/` は `lib/` と同じ構成にする。
2. 次のテストを必須とする。
   3. `.pero` の保存から復元までの往復(全種類のオブジェクトを含むモデル)
   4. 整合性確認(9.4)の各修復パターン
   5. 生成用JSON(付録B)から `postgresql.post`、`mysql.post`、`sqlserver.post` が出力するSQLの期待値の比較(サンプルのモデル5種以上。MySQL・SQL Serverは実サーバーでの確認はしていない)
   6. リレーションシップの追加(外部キー列の自動作成、7-5)と、依存関係の連動(7-6)
   7. 共通列の展開(8.2-3)と、参照の維持(8.2-5)
   8. 用紙ページの増減(5.2-4)
   9. Undo / Redo と、キャッシュの再生(9.1、9.2)
10. `flutter analyze` の警告を0にする。
11. SQLインポート(9.11)のテストも必須とする: インポート用ポストファイルの解析結果(SELECT → `import_XX`、INSERT / UPDATE は解析できないもの)、モデルへの変換と保存の往復、追加取り込みと同名の扱いとUndo、コマンドの再生、解析できないものの保存、ひな形(9.12-5)の動作、メタ情報の `role`、タブの◀▶(3.2-5)。

### 11.8 インストーラー(Inno Setup)
1. スクリプトは `inno/pero.iss` に置く。日本語のみ対応する。
2. 生成するインストーラーのファイル名は `pero_{バージョン}.exe`。バージョンは `pubspec.yaml` の `version`(`+` より前)。
3. 背景画像(ウィザード画像)は `assets/icons/pero.png`。アンインストールのアイコン、セットアップのアイコンはアプリアイコンにする。
4. インストール時に、GitHub の release に置いた zip(`PERO-v{バージョン}-windows-x64.zip`)をダウンロードして展開する。
5. 起動時に GitHub の最新リリースを検索し、このインストーラーより新しい版があれば知らせる(失敗しても続行する)。同じ AppId への再インストールは上書き更新になる。
6. CLI(`C:\Users\<ユーザー>\AppData\Local\Programs\Inno Setup 7\ISCC.exe`)での生成は `inno/build_installer.ps1` で行う。生成物は `build/windows/setup` に置く。`-Upload` を付けると、`gh` で release(zip と同じ場所)へ配置する。

### 11.9 SQLの取り込みツール
1. `tool/sql_to_pero.dart` は、PostgreSQLのDDL(SQLファイル)から `.pero` を生成する一回限りのツール(アプリ本体には含めない)。データベースへの接続はしない(0.3-2)。
2. 取り込む対象: テーブル、列、主キー、ユニーク(NULLS NOT DISTINCT を含む)、インデックス、CHECK制約、外部キー(自己参照、DEFERRABLEを含む)、ファンクション(依存テーブル・ビューを本体から判定)、トリガー(引数、UPDATE OFを含む)、CREATE VIEW(SQLビュー)、CREATE TYPE(複合型、列挙型)、COMMENT ON(テーブル、列、ビュー、ファンクション)。
3. 取り込めなかった要素は、モデルの終了クエリにコメントとして残し(生成SQLの最後に出力される)、結果メモにも出力する。

### 11.10 サンプルモデル
1. `doc/sample/pms_test.pero` は、実データ(生産管理システムのDDL。テーブル263、ビュー167、リレーションシップ791)から作ったサンプル。機能(`model_providers` のモデル)ごとに「(テーブル)」と「(ビュー)」のダイアグラムを分け、全テーブルで共通の6列(symbol、remarks、update_at、update_user_id、update_user_history_id、remove)を共通列パターンにして適用している(symbolを持たないテーブルには、5列のパターン)。
2. 大きなモデルでの、自動配置(9.9)と描画(2-11)の性能の検証(`test/performance`)に使う。

1. `tables` は親から子の順(9.6-3)。各テーブルの `columns` は、位置が「先頭」の共通列、実列、位置が「末尾」の共通列の順に並べる。共通列は `origin: "common"`、実列は `origin: "table"`。
2. `type` は、対象DBの物理名テンプレートをパラメータ展開した文字列(6.3-7)。`typeCategory` は型のカテゴリ。
3. `default.kind` が `value` のとき `value` に値の文字列、`method` のとき `call` に対象DBの呼出し式(8.1-3)を入れる。
4. `primaryKey` は、PKの列がないとき `null`。名前は `{テーブル物理名}_pk`。制約名(自動の名前を含む)は、すべて解決した文字列で渡す。
5. トリガーの `body` は、プレースホルダ(`{{table}}`、`{{trigger}}`)を置換済み。`methodName` は、本体の元が入力のとき `null`。
6. `foreignKeys` の `onDelete` / `onUpdate` は、`"NO ACTION"`、`"RESTRICT"`、`"CASCADE"`、`"SET NULL"`、`"SET DEFAULT"`、または、適用しないとき `null`。
7. ビューは、`viewType` が `join` のとき `from`、`joins`、`columns`、`where` を使い、`function` は `null`。`function` のとき、`function` に `{ "name": ..., "args": [...], "columns": [ { "name": ..., "type": ..., "typeCategory": ... } ] }` を入れ、`from`、`joins`、`columns` は空にする。`expr` は `エイリアス.物理名`。
8. 生成前検証(9.5)のエラーがあるモデルでは、生成用JSONを作らない。

9. 形式2(apiVersion 2)で追加したキー。
   - `model.dropBeforeCreate`(真偽値)、最上位の `schemas[]`(出力に使うスキーマ名。出力にスキーマを含めないときは空)
   - 最上位の `userTypes[]`(`name`、`kind`、`fields[]`(`name`、`type`)、`values[]`)。使われる型が先になる順
   - `methods[]`: `comment`、`args`、`afterViewId`(ビューへの依存があるとき、最後に作成されるビューのID。なければnull)、`afterTableId`(ビューへの依存がないとき、依存テーブルのうち最後に作成されるテーブルのID。ファンクションのみ。なければnull)
   - `tables[]`: `schema`、`checks[]`(`name`、`expression`)。`uniques[]` の各要素に `nullsNotDistinct`。`columns[].default` に `expression`
   - `triggers[]`: `args`、`updateColumns[]`(列名。空はテーブル全体)
   - `foreignKeys[]`: `childSchema`、`parentSchema`、`deferrable`(`"DEFERRABLE INITIALLY DEFERRED"` など。なければnull)
   - `views[]`: `schema`、`sql`(`viewType` が `sql` のときSELECT文。ほかはnull)。`from` と `joins[]` に `schema`
10. 形式3(apiVersion 3)で追加したキー。
   - `userTypes[]`: `schema`(エンティティと同じ規則で決めたスキーマ。出力にスキーマを含めないときは空)、`comment`。`fields[].type` と、列の `type`・ビューの戻り列の `type` は、ユーザー定義型のとき `スキーマ.型名` の形
   - `methods[]`: `schema`(外部定義は空)。`triggers[]` に `methodSchema`、関数ビューの `function` に `schema`

| real | real | なし | number | `real` | `FLOAT` | `real` | `REAL` |

2. `auto` を参照する外部キー列の型は `integer`(6.3-8)。

## 付録D. 仮定の一覧

本書で、明示の指示がないまま置いた既定値。変更するときは、本書の該当箇所を直す。
1. Deleteキーは「このダイアグラムから外す」、Ctrl+Deleteは「モデルから削除」(4.2-4)。
2. 新規テーブルは、列「ID」(型auto、PK)を1つ持つ(4.2-2)。
3. 物理名の形式の既定は `^[A-Za-z_][A-Za-z0-9_]*$`(6.7-1)。
4. 参照規則を「適用しない」とPK連動の関係(7-6-3、7-6-4)。「依存関係を有効にしても、ON DELETEとON UPDATEがともに『適用しない』ならPKに含めない」と解釈した。
5. 共通列は、仮想列方式。除外フィルタを持つ。同名の衝突は先に存在する方を優先する(8.2-3)。
6. 外部キー列の自動作成の物理名は `{親テーブル物理名}_{親列物理名}`(7-5-4)。
7. 最近使ったファイルの数の既定は10、バックアップの既定は有効(10.2)。
8. 生成ファイルの改行コードの設定(既定CRLF)と、ポスト実行タイムアウトの設定(既定30秒)(10.2)。
9. 一度も保存していない新規のモデルは、キャッシュとバックアップの対象外(9.2-2、9.3-1)。
10. グリッドスナップは10px、Altで解除(3.4-1)。
11. 色の既定値(10.2)。補足には背景色を設けない。ヘッダの背景色は文字種類とテーブルのヘッダ色を1つにまとめた。
12. 標準型の4DB分の物理名は初期値(付録C)。
13. テーブルの幅は最小160px、最大480px(6.1-7)。
14. 画像出力はPNGとPDF。1辺16000pxの上限(9.8)。
15. 用紙ページはIDを持たず、(行, 列)で識別する(5.2-3)。
16. 予約語の警告は、postgresqlのみ(9.5-2-5)。
17. ビューのソースはテーブルのみ(6.6-1)。
18. 論理名は重複を許す。ダイアグラム名は重複不可(6.7)。
19. 単一インスタンスで動作する(2-7)。
20. トリガーのタイミングはBEFORE / AFTERのみ(INSTEAD OFは対象外。6.5-2-3)。
21. 「UPDATEの対象はテーブルか列か、またはその両方」は、UPDATEを「テーブル全体」か「指定した列」かで選び、INSERT / DELETE と組み合わせられる形で実装した(6.5-2)。
22. 「空文字の型を正式に定義する。代替法を採用」は、標準メソッド「空文字」(`empty_string`)で表す形で実装した(6.2-4、8.1-15)。
23. 「出力設定にスキーマを含めるBool」は、モデルのプロパティ(5.1-2)に置いた。主キー制約名のプリフィクス/サフィックスと、再実行用DROPの有無は、設定(10.2)に置いた。
24. エンティティのスキーマは、そのエンティティを配置している最初のダイアグラム(タブ順)で決める(5.2-1)。
25. ユーザー定義型は、型(6.3)の一種として実装し、PostgreSQLの物理名だけを持つ。生成では、型のスキーマ(空ならモデルのスキーマ)を付ける(6.3-8、9.6-25)。
26. 自己参照のリレーションシップは、依存関係を無効にして作成する(7-1)。
27. ファンクションの依存テーブル・ビューの自動判定は、取り込みツール(11.9)とSQLインポート(9.11-14-18)だけが行う。アプリの編集では手動で選ぶ。
28. 検索のハイライトは、描画できるオブジェクト(テーブル、ビュー、列行)にだけ表示する。トリガーと関数は、キャンバスに描かれないため、トリガーを持つテーブル、関数を使う列行・関数ビューで表す(3.9-13、3.9-14)。
29. 検索ボックスの入力は、確定を待たず、入力のたびに検索する。
30. サイドメニューの幅は200px(3.1-3)。「ビューの追加(結合ビュー)」などが1行で収まる幅とし、収まらない文字は縮小する。折りたたみは、幅を0にするスライドとし、閉じている間はキー入力・クリックを受け付けない(3.1-6)。
31. 描画のバッファリングは、エンティティ1つ分のPictureをモデル・表示設定・テーマの世代ごとに保持する方式とした。倍率40%未満は、列行を省略して見出しだけを描く(2-11)。
32. 自動配置は、実行後に配置した範囲の左上へスクロールする。大きなモデルでは、配置が元の表示範囲の外へ出るため、結果が見えなくなるのを避ける(9.9-10)。
33. 「使えるポストファイルが1つもない」は、メタ情報が読めて `apiVersion` が合うポストファイルが1つもない、と解釈した(9.10-1)。
34. 「ポストファイルのメタデータから、どのデータベースを適用するか判断する」は、生成時にモデルの対象DBをポストファイルの種類へ自動で合わせる(確認ダイアログは出さない。Undoできる)と解釈した(9.6-1-2)。以前の「対象DBの不一致の警告(続行 / 中止)」は廃止した。
35. ポストファイルの「ロック」は、生成の間、排他のファイルロックで開いたままにして、書込み・削除・名前の変更を防ぐ方式とした(Windows)。ポストフォルダの走査(9.10-1)は、メタ情報を読むだけで、ロックしない。
36. 「種類(kind)にポストファイルを関連付けする設定項目」は、設定画面の1行のテキスト(`ファイル名=種類` をカンマ区切り)とした(10.2)。
37. 「ユーザーテーマ」は、theme_lib のテーマJSONのファイルを設定で指定する方式とした。ユーザーテーマは、ライト/ダークの両方をJSONが持てるため、モードはシステムに従う。キャンバスの配色(10.2の色の表)は、従来どおりライト/ダークの別で持ち、テーマの切り替えに連動する。
38. 色テーマの既定表示は theme_lib の組み込み既定テーマ(`default`)に変わる。ダイアログ・入力欄・ボタンの見た目は、このテーマに従う(密度は従来どおりコンパクト)。
39. 読込中のオーバーレイは、読込の処理(別Isolate)と、読込後の最初の画面の描画が終わるまで続ける。表示するメッセージは、ファイル名だけとし、進捗(割合)は表示しない(4.1-4)。
40. 生成ファイルの拡張子が `post` のとき(設定)は、ポストファイルと混同するため、`sql` に置き換える(10.2)。
41. 改行コードの変換で引用符を判定するとき、`--` と `/* */` の中の引用符は無視し、PostgreSQL は `E'...'` のバックスラッシュ、MySQL はすべての文字列のバックスラッシュのエスケープを扱う。ドル引用符(`$$`)は文字列とみなさず、中の引用符を判定する(9.6-5)。
42. 標準型「varchar(長さなし)」のID は `varchar_nolen`。MySQL は `TEXT`、SQL Server は `varchar(max)` とする(付録C)。
43. 型・メソッドのスキーマは、出力にスキーマを含める設定(5.1-2)のときだけ使う。apiVersion は、付録Bの変更に合わせて3に上げた(9.6-22)。
44. ヒットへの移動は、ヒットしたエンティティ単位(列行や関数の個別のヒットではなく)とし、ID昇順で巡る(3.9-16)。
45. ダイアグラムの切替ショートカットは、Ctrl+Tab / Ctrl+Shift+Tab(循環)と Ctrl+1〜9(4.5)。
46. テキスト入力中(入力欄にフォーカスがあるとき)は、コピー(Ctrl+C)、貼り付け(Ctrl+V)、全選択(Ctrl+A)、元に戻す / やり直し(Ctrl+Z、Ctrl+Y、Ctrl+Shift+Z)、Delete、複製(Ctrl+D)、Ctrl+Delete を、入力欄の操作として扱い、図形の操作には使わない(4.5)。
47. メタ情報の `role` の既定は `export`(9.6-4)。インポート用ポストファイルは、エクスポート用の一覧(対象のデータベースの候補、生成。9.10-5)には出さない。
48. 共通ヘルパのファイル名は `pero.lib.js` で、ポストファイルと同じフォルダに置く。ひな形は `post\template`(9.12)。既存の同梱ポストファイル(エクスポート用)は、ヘルパを使う形に書き換えない。
49. インポート結果の列の型は、PostgreSQL互換の型名の文字列を解釈する。ほかのデータベースのインポート用ポストファイルは、`typeId`(付録Cの標準型のID)などを直接指定してよい(付録E)。
50. インポートの実行タイムアウトの既定は120秒(10.2)。約1.3MBのSQL(テーブル263、関数411、トリガー616)で、解析は数秒。
51. FROM句のないSELECT(`SELECT 1`、`SELECT func()`)は、コマンドとみなして取り込まない(9.11-8)。
52. 取込先に同名のテーブル・ビュー・メソッド・型があるときは、取り込まない(上書き、改名はしない。9.11-14-19)。
53. インポートで追加するビュー `import_XX` の連番は2桁ゼロ埋めで、99を超えたら3桁以上になる(9.11-8)。
54. タブの◀▶ボタンは、収まらないときだけ表示し、1回に240pxずつ移動する(3.2-5)。
55. 新しいモデルへのインポートは、未保存の無題として開くので、キャッシュの復旧の対象外(9.2-2)。保存すると、以後は通常どおり記録する。
56. インポート結果の変換(`lib/importer`)は、PostgreSQL以外のデータベースでも、関数・トリガーの本体を、インポート結果の `dialect` のタブへ入れる(付録E)。

## 付録E. インポート結果(インポート用ポストファイルの出力)

インポート用ポストファイルの `main(jsonText)` が返すJSON。入力は `{ "files": [ { "name": "a.sql", "text": "..." } ] }`。`pero.ImportResult`(9.12-4)が組み立てる。名前は物理名。引用符なしの識別子は小文字にそろえる。

```jsonc
{
  "apiVersion": 3,
  "dialect": "postgresql",            // 関数・トリガーの本体を入れる対象DB(付録A: targetDb の値)
  "tables": [
    {
      "name": "orders", "schema": "", "file": "a.sql", "line": 10,
      "columns": [
        {
          "name": "id", "type": "serial", "notNull": true, "default": null,
          "primaryKey": false, "unique": false,
          "references": { "table": "customers", "columns": "id" },   // 列に付けた REFERENCES(省略可)
          "check": "id > 0",                                          // 列に付けた CHECK(省略可)
          "typeId": "integer", "length": null, "precision": null, "scale": null   // 省略可。あるとき type より優先
        }
      ]
    }
  ],
  "constraints": [
    { "kind": "primaryKey", "table": "orders", "name": "orders_pkey", "columns": ["id"] },
    { "kind": "unique", "table": "orders", "name": "", "columns": ["code"], "nullsNotDistinct": false },
    { "kind": "check", "table": "orders", "name": "", "expression": "qty > 0" },
    {
      "kind": "foreignKey", "table": "orders", "name": "orders_fk", "columns": ["customer_id"],
      "refTable": "customers", "refColumns": ["id"],
      "onDelete": "cascade", "onUpdate": "", "deferrable": ""
    },
    { "kind": "index", "table": "orders", "name": "orders_idx", "columns": ["code"], "unique": false }
  ],
  "triggers": [
    {
      "name": "orders_trg", "table": "orders", "timing": "before",
      "events": [ { "event": "update", "columns": ["qty"] } ],
      "forEach": "row", "when": "", "function": "touch", "args": ""
    }
  ],
  "functions": [ { "name": "touch", "schema": "", "args": "", "returns": "trigger", "body": "CREATE FUNCTION ...;" } ],
  "views": [ { "name": "v1", "schema": "", "sql": "SELECT ...", "replace": false, "fromSelect": false } ],
  "types": [ { "name": "color", "schema": "", "kind": "enum", "values": ["red"], "fields": [] } ],
  "comments": [ { "kind": "table", "target": "orders", "text": "注文" } ],
  "unparsed": [ { "kind": "INSERT", "reason": "…", "text": "INSERT ...;", "file": "a.sql", "line": 20 } ]
}
```

1. 配列の順序は、SQLの出現順。`constraints` は、主キー → そのほかの制約 → インデックスの順にアプリが適用する。
2. `name` が空の制約・外部キーは、自動の名前(6.4、7-4)にする。
3. `onDelete` / `onUpdate` は、`no action` / `restrict` / `cascade` / `set null` / `set default` / 空(適用しない)。`deferrable` は、`immediate` / `deferred` / 空。
4. トリガーの `timing` は `before` / `after`、`events[].event` は `insert` / `update` / `delete`(`update` の `columns` は `UPDATE OF` の列)、`forEach` は `row` / `statement`。`function` は、`functions` で定義した名前。
5. `types[].kind` は `enum` / `composite`。複合型は `fields[]`(`name`、`type`)、列挙型は `values[]`。
6. `comments[].kind` は `table` / `column` / `view` / `function` / `type`。`target` は、SQLの対象の表記(列は `テーブル.列`、関数は `名前(引数)`)。
7. `views[].fromSelect` が真のビューは、コマンドではないSELECTから作ったもの(9.11-8)。
8. `unparsed[]` は、解析できなかった文(9.11-9、9.11-10)。ポストファイルが解析できないと判断した文は、必ずここへ入れる(捨てない)。
9. 未知のキーは無視する。`apiVersion` は、付録Bと同じ値とする(9.6-4)。
