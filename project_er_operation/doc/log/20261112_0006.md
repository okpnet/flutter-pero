## PostgreSQL に接続して生成する仕組みの検討

SQLファイルからの生成は、スキーマの大半(テーブル、列、型、キー、トリガー)を取り込めた。取り込めなかった部分(A-1〜A-6、B-1〜B-5)は、SQL の構文を自前で解析しているために起きた制約である。データベースへ接続して生成する案を、次のとおり整理する。

| 観点 | SQLファイルを解析(現状) | PostgreSQLに接続して取得 |
|---|---|---|
| 情報源 | DDL の文字列 | システムカタログ(`pg_catalog`、`information_schema`) |
| 精度 | 構文の揺れ(大文字、省略形、コメント)に弱い | 正規化済みで安定。`pg_get_viewdef`、`pg_get_constraintdef`、`pg_get_triggerdef`、`pg_get_functiondef` で定義文を得られる |
| ビュー | 取り込めない | 定義文を取得できる(取り込み先の表現はA-1の提案が前提) |
| 外部キー、遅延可否 | 文字列の解析 | `pg_constraint` の `condeferrable` / `condeferred` で取得できる |
| 前提 | SQLファイルだけ | 接続情報、実行中のDB(今回は docker のテスト環境) |
| 仕様 | 範囲内 | 0.3-2 で「DBへの接続、リバースエンジニアリング」はv1の対象外 |

提案する方式:
1. **別ツールとして作る**(推奨)。アプリ本体には接続機能を入れず、`tool/` に「PostgreSQL → `.pero`」の変換ツールを置く。0.3-2 を守りつつ、今回の `Importer` の出力部分(モデルの組み立て)を共用できる。
2. 取得する範囲: テーブル、列(型、NOT NULL、デフォルト)、主キー、ユニーク、インデックス、外部キー(参照規則、遅延可否)、トリガー、関数、ビュー(定義文)、コメント。
3. 接続: Dart の `postgres` パッケージ(純Dart)を使う。接続文字列は環境変数で渡し、`.pero` やログには残さない。
4. 条件: 先に A-1(SQLで定義するビュー)、B-1(遅延可否)、A-5/A-6(トリガーの引数、UPDATE OF)の仕様を決める。決めないと、接続しても保持先がない。
5. 次の手順: (a) docker のテスト環境へ接続して、スキーマ `tests` から取得できるか試す。(b) 取得結果と、今回のSQLファイルからの結果を比較して、差を確認する。
